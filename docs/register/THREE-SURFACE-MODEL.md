# Tower Register — Three-surface model

**As of:** 2026-07-27  
**Status:** Locked — guides Register reshape and click-through work

---

## The three surfaces

| Surface | Route / location | Job |
|---------|------------------|-----|
| **Register** | `/register` | Theory workspace — complete product truth on paper (left panel passes). Future: DS-I lo-fi click-through on the right canvas. |
| **Product** | `/` (live app) | Translation destination — hi-fi UI consultants use. Not edited during Register passes. |
| **Console** | Docs mode in product | Live holon map — what exists in the running app right now. |

Register is **not** a duplicate of Console. Console answers *what is mounted*. Register answers *what the product must be*, with pass-ordered theory and (later) lo-fi functional proof.

---

## Left vs right in Register

| Side | Job | Fidelity |
|------|-----|----------|
| **Left panel** | Pass-ordered theory (Seed → World → … → Wiring → Components) | Text, structured joins, collapsible Implementation |
| **Right canvas** | Detail for selected pass; How graph when Function leaf work needs it; **future** DS-I click-through inhabit | Lo-fi gray when CT lands — not product tokens |

Tower keeps its **Register visual design** (Inter, tree typography, panel chrome). Import **hierarchy and interaction shape** from omcoda methodology — not Trove scaffolding colors or layout widths.

---

## Pass sequence (authoritative)

```text
Seed → World → Personas & Function → SME → Enrichment → Furnish → Wiring → CT Plant → Translation
```

**Text-first law:** Left-panel writing (consideration → solution → click-path Implementation) verifies congruence without building click-through at each pass. Batch theory, then one CT plant pass.

**PM product law:** Implementation writing follows production-app navigation — persistent left nav, modules revealed upfront, no clunky reveal-on-click patterns (Trim anti-pattern).
