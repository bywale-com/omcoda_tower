## What the session was trying to establish

Claim 23 denies a send when the consent row’s `silenced` is true or its `status` equals `silenced`. The silence route that sets the boolean does not name `status`. Journal 018 left that write because the get does not read the column, and because the migration’s one-time `UPDATE` is a backfill rather than this upsert. If some reader treats `status` as the silence, the boolean arm does not make the default safe. If no reader does, the default can stand.

## What the statement and the backfill do

`handleConsentSilence` in `server/wire-service/stores.ts` inserts `basis` `none` and `silenced` true, with the body’s contact, firm, and source. On conflict of `(contact_id, firm_id)` it sets `silenced` true, replaces `source`, and sets `updated_at`. It does not assign `basis` on conflict, and it does not assign `status` on either clause. `supabase/migrations/004_machine_tables.sql` adds `status` as `TEXT NOT NULL DEFAULT 'unsequenced'`, checked to `unsequenced`, `waitlisted`, `sequenced`, or `silenced`. The comment says the table is extended for waitlisted. A new row from this route therefore stores `silenced` true and `status` `unsequenced`. A conflict leaves whatever `status` was already there.

The same file then runs one `UPDATE`. When `silenced` is true it sets `status` to `silenced`. When `basis` is `express` or `implied` it sets `status` to `sequenced`. The `WHERE` keeps the write to rows that are still `unsequenced` and already have that boolean or that basis. The statement runs with the migration. It is not a trigger. Seeds that insert consent after it, `supabase/seeds/004_contact_seat.sql` and `supabase/seeds/005_contact_workspace_fill.sql`, name `basis` and `silenced` and do not name `status`, so those rows keep the default. `docs/register/SYSTEMS-GOAL.md` already says the cascade does not write `waitlisted` or `sequenced`. The backfill is how rows that existed at the `ADD COLUMN` were kept off a default that would have mislabeled them. It is not a rule that every later insert copies the boolean into the column.

## Why that changed the reading

The backfill shows that, at the moment the column was added, a silenced row left at `unsequenced` would have been the wrong label for anything that read the new word. What the search found is that no later reader classifies the contact from that word. The gate’s status arm fires only for the literal `silenced`. The seat, the get, door 1, and the stand-in use the boolean. The audit’s ready flag does not consult the table. A branch that could read `status` off claim 15’s re-read is not configured, and the live loader still returns null for the table. `SYSTEMS-STORY` §6 still says a contact is sequenced, silenced, or unsequenced, and claim 15 still locates that word on the column. The readers that stop outreach read the boolean migration 003 stored before the column existed. Leaving the default does not show the operator a different contact, and it does not let this firm’s send through on another firm’s row. Claim 23 already named that row.

The same search showed the other direction of the status arm. `handleContactSeatConsent` sets `silenced` false and does not assign `status`. `handleConsentSet` on conflict does not assign `silenced` or `status`. The one-time `UPDATE` is the production statement that stores `status` `silenced`. A row it marked that way stays on the status arm after a later Agree clears the boolean. That is a real deny. It is not produced by this upsert, which never stores `silenced` in the column. It was left as the next write to judge.

## What was considered and set aside

Assigning `status` `silenced` on both the insert and the conflict would copy the backfill’s silenced arm onto every call. The backfill was for rows present when the column appeared. No reader treats the default as an unsequenced contact. On conflict the assignment would replace a `sequenced` or `waitlisted` value this route did not come to change, and `SYSTEMS-GOAL` already says the cascade does not write those two values.

Assigning `silenced` only on the insert, and keeping the previous `status` on conflict, was set aside because the boolean covers both shapes. A new silence and a repeated silence would then store different words, and no reader asks for that split.

Copying the backfill’s full `CASE`, so an `express` or `implied` basis became `sequenced`, was set aside because this statement sets `silenced` true and, on insert, `basis` `none`. The silenced arm of that `CASE` would win on every row the call touches. The sequenced arm would not run. `consent_records.sequenced` remains a catalog label and a matcher for `sequence_id`, with no dispatch and no write-set row. The status decision did not need that event.

Using the story’s three-way word, or the system-map enum, as a reason to write the column anyway was set aside because the distinction does not change the operator’s desk, which firm’s consent binds the send, or a commercial obligation. The CASL geography in §6 stays unnamed. Retuning the gate so it stops reading `status` was set aside because claim 23 kept the arm, and this route does not produce the value that arm denies.

`handleContactSeatSilence` and the hard-bounce upsert also omit `status`. They stay other writers of the pair. They were not used to choose this route’s columns.

## What was settled

`handleConsentSilence` does not assign `status`. An insert keeps `unsequenced`. A conflict keeps the previous `status`. The boolean arm denies the row. No founder question. The split that would need the founder is a reader that treats `unsequenced` as the contact’s silence, or a desk that shows the column. Neither is there. No migration.
