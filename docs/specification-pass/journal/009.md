## What the session was trying to establish

Claim 14 had left this dispatch as the next site, and it had left the key looking unlike `halt-` or `cfail-`. The silence handler upserts one pair, sets `silenced` true, and dispatches with no `writes`. The write-set names `consent_records` alone. `writesFromPayload` returns when `payload.writes` is an array and drops an element that has no string `id`. A table with no `id` column cannot be pointed at the way claim 13 pointed at `campaign_failure`. Claim 8 had already met that shape on the audit tables: no column named `id`, `RunWrite` still `{ table, id, contact_id }`, and a later execution that overwrites the same key cannot be “what this run wrote.” The open question was whether consent is that kind of overwrite. One current row per contact and firm, and a history of decisions, satisfy “name the row” in different ways. One of them would mint a column or a table. The other would put the existing pair on the pointer the channel already has. Which one the product already requires had to be read off the writers, the send gate, and the consent face, not off the missing `id`.

## The silence handler, and the row it upserts

`handleConsentSilence` reads `contactId`, `firmId`, and `source`. It inserts `consent_records` with `basis` `none`, `silenced` true, that source, and `updated_at` now. On conflict of `(contact_id, firm_id)` it sets `silenced` true, replaces `source`, and sets `updated_at` now. It does not assign `basis` on conflict, and it does not assign `status`. Then it calls `dispatchEventToWorkflows` with `eventName: "consent_records.opt_out"`, `firmId: body.firmId`, `payload: { contactId, source }`, and `contactIds` of that one contact. There is no `writes`. The route is `POST /consent/silence`.

`supabase/migrations/003_ct_wire_stores.sql` gives the table `PRIMARY KEY (contact_id, firm_id)`. The column list is `contact_id`, `firm_id`, `basis`, `silenced`, `source`, `updated_at`. There is no `id`. Migration 004 adds `status`, default `unsequenced`, constrained to `unsequenced`, `waitlisted`, `sequenced`, or `silenced`, and backfills existing rows from `silenced` and `basis`. The silence statement does not mention `status`, so an insert takes the default and a conflict leaves the old value. Migration 020 adds `workspace_opted_out`, default false, and says the flag is a field, not email silence. The silence statement does not mention that column either.

`event_write_set` version 1, in `supabase/migrations/017_event_test_contract.sql`, names `consent_records` at ord 0 and names nothing else. The live statement writes that table. It does not skip it. The version 1 specimen is one body, Haddad, `silenced` true, source `unsubscribe.email`, and it has no `id`.

The first reading, from the missing array alone, was the claim 11 shape with nothing to put in `id`. That part held as the channel. It did not choose the string. `writesFromPayload` keeps `table`, `id`, and `contact_id`, and it drops an element whose `id` is not a string. The payload’s `contactId` is singular. The separate `contactIds` argument is the person list. With `writes` present, the function does not also build a `contact_records` pointer.

## One row, not a log

The next question was whether a later write destroys a fact the listener has to keep, which is why claim 8 stopped using `(contact_id, firm_id)` as the audit key. The consent writers were read. `handleConsentSet`, `handleContactSeatConsent`, `handleContactSeatSilence`, and the hard-bounce branch in `webhooks.ts` all upsert the same pair. None of them insert a second row. The seat consent path sets `silenced` false. The seat workspace path sets `workspace_opted_out` and leaves `silenced` alone. The bounce path sets `silenced` true and `source` `hard-bounce`. There is no consent decision table beside this one.

The readers match that grain. `consentAndHaltGate` loads `basis`, `silenced`, and `status` and denies when the contact is silenced or the basis is missing, unless the purpose is `opt-in`. `projectSeat` loads `basis`, `silenced`, and `source` for the link’s contact and firm, and it withholds the deeper form when `silenced` is set. `handleConsentGet` returns the current basis, silenced flag, and source. `isWorkspaceOut` and the workspace list read `workspace_opted_out` on the pair. Door 1 reads current silenced rows for the firm, newest `updated_at`, limit 10. None of those queries name an earlier decision after a later upsert.

The faces say the same thing in the product’s words. `docs/register/how/contact-silence.md` says the Silence commit writes silenced state that engagement runners, send gates, and Book readiness read, and that further automatic outreach stops. `docs/register/how/contact-consent.md` says Agree writes consented state and Ignore writes the no-deeper state, both read by runners. `docs/register/SYSTEMS-STORY.md` §6 says the system treats contacts as sequenced, silenced, or unsequenced. That is a state of the contact, not a ledger line. `docs/register/PRIMITIVES.md` says the next step points at the writes this run made, and that guessing “latest audit for this firm” is not this node. For the audit tables, latest-versus-this-run was already two product questions, so claim 8 gave each run its own row and left “who is ready now” as a read of the latest. Consent does not have the first of those questions in any reader that was opened. The current row is the fact. A later update of the pair is that fact changing, which is what claim 14 already required the halt re-read to show when `lifted_at` is set. A history would store a second fact the story does not ask the listener to open.

The story’s silence on consent regimes was checked before it could be treated as this choice. `SYSTEMS-STORY.md` §6, and the earlier silence at §1, name CASL and SMS regimes by geography for firm→client and for the first agent→consultant text. They do not name a pointer shape. The pair can be specified without choosing a regime. That silence stays a silence.

## Where the pair sits on the pointer

`RunWrite` is `{ table, id, contact_id }`. Claim 8 put the audit run in `id` and the person in `contact_id` because those two fields were the key and neither one was the walk’s firm. Consent’s key is the person and the firm. The firm is already the walk. `handleConsentSilence` passes `firmId: body.firmId`, the same value the upsert binds. `dispatchEventToWorkflows` inserts `workflow_run.firm_id` as `opts.firmId` and calls `walkValidatedWorkflow` with that firm. `loadWriteRow` already takes that firm as an argument. Putting the firm in a new pointer field was refused under claim 10 and claim 11, because `RunWrite` has no such field. The half of the key that is not already the walk is the contact. The element has to carry a string `id` or the channel drops it. That string is the contact. `contact_id` on the element is the same contact. Both are required.

The dispatch payload therefore gains one element: `table` `consent_records`, `id` the body’s `contactId`, `contact_id` that same contact. The array follows the write-set. There is one table and one upsert, so there is one pointer.

The re-read is the primary key: `contact_id` from the pointer, `firm_id` from the walk. No order. No “latest”. No `silenced` filter, because a later writer can clear the flag and the listener has to see the row anyway. A miss returns null. The loader does not look up a column named `id`, and it does not drop the firm. That predicate is not claim 10’s `WHERE id = pointer.id`, and it is not claim 8’s `(audit_run_id, contact_id)`. The function was not retuned. It still has no branch and still returns null. Applying the pair is not a new load rule for the tables that have an `id`. `consent_records` is not in `PERSON_WRITE_TABLES`. This firing has one pointer and it carries `contact_id`, so `personIdsFromWrites` uses that field. The set was not retuned.

`contactId` and `source` stay on the payload. `contactId` is the contact-axis key. `source` is the source this call passed. A later silence replaces `source` on the row. The payload on this run still has the earlier string. The If reads the row, which is the refusal of a snapshot already recorded under claim 8. The columns a later node sees are the ones the upsert leaves: on an insert, `basis` `none`, `silenced` true, the body’s source, `status` `unsequenced`, `workspace_opted_out` false; on a conflict, `silenced` true, this call’s source, and the previous `basis`, `status`, and `workspace_opted_out`. The specimen’s `contact_name` and `firm` are not stored. Door 1 was not retuned. Its ten silenced rows are the specimen. `writeId` already falls back to `contact_id` when `body.id` is absent, which this specimen is. That is why the specimen’s `id` and this firing’s `id` are the same string. It was not a reason to change door 1.

`dispatchEventToWorkflows` still copies the payload and still sets `anyPass: true`. Claim 7’s refusal of that flag was not recut. `writes` has to be on the object passed in, because the copy is what `writesFromPayload` reads. The HTTP body is `{ ok: true }`. There is no `RETURNING`. The stand-in `silence` in `src/app/wire/standins/consentSilence.ts` stores the flag and does not dispatch. This firing is the server handler.

## The basis write, and the other writers of the same pair

`handleConsentSet` is the other route, `POST /consent`. A new row stores the body’s basis and `silenced` false. On conflict it updates `basis`, keeps the old `source` when the body omits one, updates `updated_at`, and leaves `silenced` unchanged. It returns `{ ok: true }`. It does not dispatch. `handleContactSeatConsent` is the contact’s Agree or Ignore: it sets `basis`, sets `silenced` false, and does not dispatch. There is no write-set row for a basis event.

That withholding is the distinction the firm-book branch was, and it is not the same branch structure. Firm-book is the other `scope` of `handleHaltCommit`, same event name, and the desk copy says the write itself stops sends and new enrollments. Consent set is a different route and a different event. Dispatching `consent_records.opt_out` from Agree would start every subscribed opt-out automation on a consent, and Agree is the path that clears `silenced`. The handlers already omit the call. The basis write stays the gate. This session does not add the dispatch.

Two other writers of the same pair were opened because the grain question required them, and they are not this firing. `handleContactSeatSilence` sets `workspace_opted_out` true and does not set `silenced` and does not dispatch. ## Alternatives, and why they lost

A surrogate `id`, and a `cfail-` pointer, lose because the table has no such column and the primary key is the pair. The writers would have to stop upserting. The specimen would grow an `id` that `writeId` would then prefer, which is the specimen-identity problem claim 8 already refused. No migration was written.

Splitting the grain into one row per decision, with “current consent” as a latest read, loses because that split was the audit problem. The consent readers and the two How leaves ask for the current state. A later agree that clears `silenced` is the state changing. The re-read has to see it. A history table would be the shadow copy claim 8 refused. The regime silence does not force the split. The pointer is nameable without it.

Putting the firm in `pointer.id` loses because the walk already is that firm, and the contact axis and `writeId` already use the contact. An encoded `contact|firm` string loses because claim 8 refused an encoding and the loader would be parsing a private format.

Mapping `contactId` inside `writesFromPayload` loses because claim 7 refused a second channel. The function returns on `writes` and would otherwise build `contact_records` from a contact list. The caller holds the contact the upsert used.

Leaving the row off the handle, for the If to read `contactId` and `source` on the payload, loses for the reason claim 7 already gave. The pick is `mappedWrites` and `loadWriteField`.

Selecting the newest silenced row, or any row for the contact, loses because this firing has the pair in hand. Door 1’s limit of ten is the specimen. The gate’s `LIMIT 1` is the send check. There is one row per pair, so “latest” is not a second row. It is the wrong reader.

Loading by `contact_id` alone loses because the primary key includes the firm and the walk has it. The gate omits the firm. The pointer does not copy that omission.

Filtering the re-read to `silenced` true, or to `status` silenced, loses because a later seat agree clears `silenced` and the silence upsert does not maintain `status`. The row has to remain the handle after those updates. Door 1’s filter stays the specimen.

Dispatching the basis routes as this event loses because the named event is the opt-out and Agree clears silence. The handlers already withhold the call. Adding the bounce or the workspace opt-out as elements of this array loses because this dispatch does not perform those writes, and the workspace flag is a different column the migration already separated. The shared pair explains the re-read. It does not merge the dispatches.

Adding `contact_records` loses because the write-set does not name it. Adding the table to `PERSON_WRITE_TABLES` loses because this firing has one pointer and `contact_id` is set. Dropping `contactId` or `source` loses because `contactId` is the contact-axis key and both are already on the payload. Adding `basis`, `status`, `firmId`, or the specimen’s display name as root scalars loses because the firm compare already uses `opts.firmId` and the row holds the columns. Copying the row onto the pointer loses because `loadWriteField` re-reads. Requiring `RETURNING` loses because the statement produces no new id. The identity is the pair the body passed. Retuning `status` on the insert loses because the pointer names the row either way, and the boolean is the column this handler writes.

No founder question. The write-set chose the table. The primary key chose the pair. The walk already holds the firm, so both pointer fields are the contact. The basis route stays the gate, in the same sense the firm-book halt stays the gate: runners read it, and it does not start this listener. A listener that is already subscribed starts from this contact at this firm. A later update of that pair is visible on the re-read.
