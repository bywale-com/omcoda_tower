## What the session was trying to establish

Claim 11 had already left the four eligibility rows off the fact pointer, because `event_write_set` names them on `eligibility.changed` and the cascade dispatches that event with no `writes`. What it had not done was say which inserted rows that one dispatch places on the array, what the primary key of each row is, or how a later node tells two rows of the same table apart when one firing inserts more than one. Two ways of naming the inserted ids can both be technically sound and still disagree about whether one listening run sees every contact, and about whether a row the cascade also writes is part of this handle.

## What the cascade inserts, and what it sends

`runContactEligibilityCascade` in `server/wire-service/machine.ts` loops `opts.contactIds`. For each contact it inserts four rows and keeps the ids in variables: `eval-${randomUUID()}` into `eligibility_evaluations`, `eres-${randomUUID()}` into `eligibility_results` with `evaluation_id` set to the evaluation id, `sig-${randomUUID()}` into `signals` with kind `eligibility_determination` and payload `{ resultId, anyPass }`, and `mot-${randomUUID()}` into `motion_decisions` with reason `{ signalId, precedence: "mp-1" }`. `anyPass` is the constant `true`. The motion expression is `anyPass ? "reactivation" : "nudge"`, so the stored motion is `reactivation`. After the loop the function calls `dispatchEventToWorkflows` once. The payload is `{ ...opts.eventPayload, anyPass: true, motion: "reactivation" }`. `contactIds` is the same list. There is no `writes`.

That single dispatch is why a multi-contact list is one firing. The ids already exist in the loop before the call. The returned `cascade` array is a different object, `{ contactId, evaluationId, resultId, signalId, motionId, motion }` per contact. `handleFactWriteback` spreads it into the HTTP body. The dispatch does not receive that body.

`supabase/migrations/004_machine_tables.sql` gives each of the four tables `id TEXT PRIMARY KEY`. `eligibility_results.evaluation_id` references the evaluation and is not the result’s key. The contact index on `eligibility_results` is `(firm_id, contact_id, created_at DESC)`. There is no column problem of the audit kind. The pointer id is that primary key.

`event_write_set` version 1, in `supabase/migrations/017_event_test_contract.sql`, names `eligibility_evaluations` at ord 0, `eligibility_results` at ord 1, `signals` at ord 2, and `motion_decisions` at ord 3. The version 1 specimen puts two contacts on one event, grouped by table: Okonkwo then Alvarez for each table. The live cascade’s inserts match those four names. On the path that dispatches to a workflow, it does not skip a named table and it does not insert a fifth table before the dispatch.

## How a later node tells those rows apart

`pickWrites` filters by table, so naming `motion_decisions` does not read the evaluation. The foreign keys are columns: `evaluation_id` on the result, `payload.resultId` on the signal, `reason.signalId` on the motion. A node that holds one pointer re-reads that row. It does not need the sibling id on the pointer.

`docs/register/PRIMITIVES.md` says a person-row write splits people. These rows are one per contact. `evalIfPick` splits only when the picked table is in `PERSON_WRITE_TABLES`. The four tables are not in that set. A table pick with no contact therefore reads the first pointer of that table, and every `ctx.contactIds` takes the same branch. That is the live behaviour. The specified behaviour is the split claim 10 already described for the other per-person append tables: test each contact against the pointer whose `contact_id` is that contact, then load that pointer’s id. The row id is not a person. Every pointer carries `contact_id`, because adding the tables to the set and omitting `contact_id` would make `personIdsFromWrites` treat `eval-` as a person.

The loop does not dedupe. A repeated contact id inserts a second quartet, and the existing `find` takes the first pointer that shares `contact_id`. A pick that names the primary key selects that row. That find was already parked under the field chip. It was not retuned.

`loadWriteRow` falls through and returns null for all four. Claim 10 already requires an `id` primary key to load `WHERE id = pointer.id`, with no firm predicate, no contact predicate, and no “latest”. Applying that predicate is not a new load argument. The function was not retuned. `handleBoardDetections` still reads `DISTINCT ON (contact_id) … created_at DESC` for results, signals, and motions. That is the desk’s current row. It is not this handle.

Door 1 in `eventTest.ts` is still the specimen. It takes the newest eight evaluations for the firm, the results whose `evaluation_id` is in that set, every `eligibility_determination` signal for those contacts, and every motion for those contacts. The signal query does not match `payload.resultId`. The motion query does not match `reason.signalId`. Those extra history rows are not this firing. Door 1 was not retuned.

`evalBranch` reads `eligibilityPass` and `triggerPayload.motion`. The walker does not call it. The branch and If nodes call `evalIfPick`. The seed workflow `wf-eligibility-reactivation` has a branch labelled “Reactivation-worthy?” with no compare and no `pickTable`, so `evalIfPick` has no compares and returns false. Placing the four pointers does not make that branch read `motion_decisions.motion`. That graph was not specified.

## The rows that are not this array

When `dispatched.length === 0`, the same function calls `enrollAndActuate` for `tpl.reactivation.v1`. That function inserts `enrollment` and `active_attempts`. `fireFirstStep` is omitted, and the default is to fire, so it also calls `writeEngagement`, which inserts `engagement_records`. A halt returns before the enrollment insert. The write-set does not name those tables. The inserts run only when no workflow fired, so there is no listening run to place them on. They are a contract break if the write-set is read as every table the function may insert. They are not a missing element of the listening pointer. The enroll was left unspecified.

Callers write rows before the cascade. The fact handlers write `fact_writebacks`. The reference handler writes `reference_versions`. Those tables are not in this write-set. `referenceId` stays a scalar. The fact row is claim 11’s dispatch, which happens after the cascade returns.

`scripts/verify-automations-alive.ts` dispatches the event name with `anyPass`, `motion`, and one contact id, and it does not insert the four rows. That script is not this firing.

When the contact list is empty, the loop inserts nothing. The specified `writes` is an empty array. `dispatchEventToWorkflows`, for an every-firm audience with an empty contact list, selects every `contact_records` id for the firm and walks them. That substitution was seen. It is not the four rows. It was not specified.

The constant `anyPass` was seen and left. The cascade does not consult a pathway rule. `docs/register/SYSTEMS-AUTOMATIONS-ASCRIBE.md` A2 says the walker does not evaluate the field-operator-constant rows, and that `rule_eligibility_pathway` is a pass flag rather than that matrix. What a real pathway evaluation would store was not specified. The pointer names the row the insert wrote, whose pass flag is the constant.

## Alternatives, and why they lost

Mapping `evaluationId` and the other cascade keys inside `writesFromPayload` loses because claim 7 refused a second channel, the function already returns on `writes`, and the HTTP object is not the dispatch argument. The cascade holds the ids the inserts used.

Leaving the ids on that returned object, or on the `motion` scalar, loses for the reason claim 7 already gave. The pick is `mappedWrites` and `loadWriteField`.

Selecting the newest row of each table loses for the reason claim 7 and claim 10 already gave. Door 1’s limit of eight, and the Board’s `DISTINCT ON`, are other readers.

One dispatch per contact loses because the function already dispatches once with the whole list, `contact_import` and `audit.completed` already put many person rows on one `writes` array, and the version 1 specimen already puts two people on one `eligibility.changed`. The primitive splits those people inside the run. A second firing model would change how many runs one reference edit starts, and it would change the fallback’s single check of `dispatched.length`.

Contact-major order loses because the registered ord is a table order and the specimen groups by table. A table pick does not depend on cross-table order. For one contact the two orders are the same four pointers.

Pointing only at the motion, or only at the evaluation, loses because the write-set names four tables and claim 7 refused a substitute row. The foreign keys stay columns.

Adding the fact row, the reference row, missing signals, or the enroll’s tables loses because the write-set does not name them.

Adding every historical signal or motion, because door 1 does, loses because this firing inserted one of each per contact.

Using `evaluation_id` or `payload.resultId` as the pointer id loses because each row’s primary key is its own `id`.

Loading the four as the audit pair, or by latest contact, loses because the primary key is `id` and claim 10 already separated that predicate from the audit pair and from “latest”.

Copying the row, or putting `firm_id` on the pointer, loses for the reasons claim 8 and claim 10 already gave.

Dropping the scalars loses because claim 7’s `anyPass` refusal was not recut, and the callers already put `form_ref`, `campaign_objective_id`, and `referenceId` on the payload. `localRefFromPayload` does not read this event. This claim does not add a case.

No founder question. The operator’s If still reads a field of a row this firing named. Two contacts are two primary keys of the same table, and `contact_id` is how the later node tells them apart. The write-set chose the tables. The primary key chose the id. The cascade’s one dispatch, and the specimen’s two people, chose one firing rather than one run per contact.
