## What the session was trying to establish

The missing array on the firm dispatch was already the pointer, and that pointer names no person. The open question was the other argument. `dispatchEventToWorkflows` will, for the default audience, invent a person list from the firm’s contacts when the caller passed none. A listening workflow whose action enrolls, tags, or audits then does that work for every one of those contacts. The firm event is the sharp case, because nothing in the firing is a person. The same function also serves the empty eligibility list and the halt body that forgot `contactId`. Three callers and two audience values looked, from the handoff, like they might need three answers. The product either already has one rule for “the firing named nobody,” or the firm case is a blast the other two callers happen to share. Which of those is true had to be read off the audience the operator saves, what a workflow is supposed to walk, and what the actions do with `ctx.contactIds`.

## The branch the dispatcher already runs

`localAxesMatch` runs first. It compares `local_contact_ids` to `payload.contactId` or, when that key is absent, to `opts.contactIds`. A trigger that stored contacts does not match a call that passed none. The fill never gets a chance to satisfy that axis. `handleMachineProvision` sends `firmId` and no contact, so a contact-local trigger does not hear this firing. Claim 16 already recorded that this event’s layers are firm only. That was not reopened. It matters here only because the people built below are not an input to the match.

For a workflow that matched, the scope is `workflow.audience_scope`. The value `select_from` is the narrow one. Null and anything else are `every_firm`. Migration 012 defaults the column to `every_firm`. The dispatcher joins those workflow columns. It does not read `workflow_trigger.scope`. `materializeTriggersFromGraph` writes that trigger column as `every_firm` and writes an empty `scope_contact_ids` on every trigger. The operator’s choice is the workflow row `handleWorkflowCreate` saves.

When the incoming list is missing or empty, `select_from` takes `audience_contact_ids` and skips the workflow when that array yields nothing. There is no `workflow_run`. `every_firm` runs `SELECT id FROM contact_records WHERE firm_id = opts.firmId`, with no `ORDER BY`, and starts the run even when the query returns no rows. When the incoming list is non-empty, `every_firm` keeps it and does not query the book, and `select_from` keeps the intersection and skips when the intersection is empty.

The resolved list is the `contactIds` argument of `walkValidatedWorkflow`. It is not copied onto `triggerPayload`. `writesFromPayload` never sees it. The walk, if that argument is still empty, fills only from `personIdsFromWrites`. Claim 16’s pointer has no `contact_id`, and `ct_firms` is not in `PERSON_WRITE_TABLES`, so that second fill adds nobody. For this firing the dispatcher’s list is the whole person list.

## Why a firm firing makes the fill the subject

The first reading of the handoff was that “every contact of the firm” might be the wrong subject for an event that is about the firm. The actions were read to see the blast. `call_agent` loops `ctx.contactIds` and calls `enrollAndActuate` with the walk’s firm and `fireFirstStep: true`. `ascribe_tag`, with no chip and no `pickTable`, tags that same list. `contactsForAudit` uses `ctx.contactIds` when it is non-empty, and the query also requires the walk’s `firm_id`. An If whose chip is `ct_firms` does not person-split, because that table is not in `PERSON_WRITE_TABLES`, so `evalIfPick` takes one branch and leaves the list intact. A firm-row condition that passes then enrolls the whole list.

That is a blast if the list is the wrong people. It is also the only way the list exists. A first provision inserts no `contact_records`. The book query is empty, the run still starts, and the audit’s contact query returns nobody. A later provision of the same id, which claim 16 already said still dispatches, walks whoever that firm has then, and the agent action enrolls them and asks for the first step. The audience rule does not know insert from conflict.

The product text was opened to see whether that blast is the intended inside. `PRIMITIVES.md` says a firm that was created is already there, and the listener does the inside: audit, agents. The same page’s action “Who this applies to” is the contacts on the automation, and it does not start a mission now. `AUTOMATIONS-FACE.md` law 31 puts that scope on events. The founder’s quotation on that page is the workflow: a firm was just created, run an audit on the contacts, then a condition, then agents. The Automations Add-contact footer is “Who this automation applies to. It does not start a mission now.” The Agents footer on the same modal is “This starts the mission now.” A19 is that Automations contacts tab. `IMPLEMENTER-FACE-PASS.md` separates it from Global/Local.

So the audience is not a filter that sits idle until the event happens to name someone. It is who the work applies to when the event fires. `ct_firms` never names someone. If the empty firing walked nobody, the audit in that workflow would have no contacts, on every provision, forever. The pointer cannot supply them. The walk will not query the book by itself. The audience is the remaining source.

## The firm cut, and where the live arm is wider than the run

The every-firm query is already one firm: `opts.firmId`, which is the firm stored on `workflow_run`. That matches the inside of the firm that was provisioned. It does not match the helper on the modal, “All contacts, every firm.” That helper was checked against the other door. `handleContactRecordsList` with `scope=every_firm` is the operator book, no firm predicate, firms first in `ContactPickModal`. `handleSequenceEnrollContacts` selects every `contact_records` row the same way, then enrolls each under `row.firm_id`. That starts the mission now, and each person keeps their own firm. A listening run has one `firmId`. `call_agent` would stamp the firing firm on every id. Copying the Agents query onto this walk would enroll another firm’s contact here. Firm isolation is already housed on `workflow_run.firm_id`. The helper is the picker. The fire-time list is the firing firm. The save path was not changed. `handleWorkflowCreate` stores the ids the operator left checked, including ids from several firms.

That storage is where the live `select_from` arm is wider than the run. When the firing passed nobody, the code uses the stored array with no `firm_id` check. Those ids become `ctx.contactIds`. The agent action enrolls them under the firing firm. `contactsForAudit` would then drop any id whose row is not in this firm, and the enroll would not. The every-firm arm already refuses the other firm. The specified `select_from` arm is the stored ids that are `contact_records` of the firing firm. When none remain, the workflow does not start, which is the skip the code already uses for an empty array. The stored array is not rewritten. Another firm’s firing resolves its own subset. The live arm does not apply this cut. That is the gap. It is not a second branch.

The in-memory fan-out in `src/app/wire/standins/machineApi.ts` was opened because it looks like a second opinion. It does not query the book. `select_from` uses the stored ids unfiltered and skips when the array is empty. `every_firm` starts a run and passes no person list. `startRun` does not walk contacts. The stand-in records that a workflow fired. It is not the person list the server enrolls.

## One branch for the other two callers

An empty `eligibility.changed` inserts nothing. Claim 12’s `writes` is an empty array. A contact-scope halt that omits `contactId` still dispatches, and claim 14’s pointer has a null `contact_id`. Both reach this function with no contact ids. The function does not read the event name. An If that needs a row the firing did not write still fails closed. The people are not a repair of a missing person on the halt row, and they are not the four eligibility rows.

The non-empty arm was left as it is. A fact’s one contact, a reference list, a halt that included `contactId`, stay that list. `every_firm` does not replace them with the book. `select_from` intersects. This claim does not add a firm predicate there, because the firing already named the people.

## Alternatives, and why they lost

Walking nobody on every empty firing loses because the provision example audits the contacts, and this firing has no other person source.

Treating Every firm as the operator book, with no firm predicate, loses because Agents enrolls each contact under that contact’s firm and starts now. This run enrolls under the firing firm. The every-firm query already cuts by that firm. The primitives’ inside is that firm.

Leaving `select_from` unfiltered loses because the picker saves the whole book and this arm would make those ids the walk. Another firm’s contact would be enrolled here. The stored selection stays. The walk takes this firm’s subset.

Skipping Every firm when the book is empty loses because the firm listen is the run. An empty book means nobody to audit yet. `select_from` skips because the operator named people and none of them are in this firm.

A separate fill for `ct_firms` only loses because the dispatcher is one branch, and claim 12 and claim 14 already enter it.

Feeding the filled list back into `local_contact_ids` loses because the match already ran on the firing’s list. Reading `workflow_trigger.scope` loses because that column is hardcoded and the dispatcher joins `workflow.audience_scope`. Putting the ids on `writes`, or into `contact_id` on the firm pointer, loses because the write-sets do not name `contact_records` for these events, and a firm id in `contact_id` is the split claim 16 refused. Copying the audience onto the payload so `writesFromPayload` builds `contact_records` pointers loses because that would make the book the handle. The handle is the firing’s rows.

Using the stand-in’s missing query as “every-firm walks nobody” loses because the stand-in does not walk. Adding `ORDER BY` loses because the live query has none, and the claim names the set.

The cross-firm `select_from` list was the split that could have gone to the founder. An operator can check people in several firms, the contacts tab shows them, and a provision of one firm could be read as “walk everyone I checked.” That changes who is acted on across firms, and the enroll asks for a first step. It did not stay a founder question. The run is already one firm. The every-firm arm and the audit query already keep that firm. The enroll stamps that firm. The inside the primitives name is that firm. The saved list is who it applies to, resolved per firing. Walking the other firm’s contact under this firm is the live arm, and it fights those decisions.

No founder question. A firing that names people keeps them, narrowed by Select from. A firing that names none walks the audience inside the firing firm. Select from with none in that firm does not start. Every firm with an empty book starts, and the person list is empty. The book is not a write.
