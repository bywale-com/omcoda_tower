## The walker writes, and the wait arm writes the old object

`tickOnce` loads open attempts, then runs `advanceTemplateCellIfDue`, then reads `attempt_wait_until` from the object it loaded. The walker copies `attempt.state` into a new object. It updates `owner_channel`, `state`, `fired_criteria`, and `window_started_at` in the database. It does not assign `attempt.state`. The loaded object still has the old `cellIndex`, and it still has the wait key if the queue had set one.

When the key is a string and its time is not still ahead of the tick, the arm copies that loaded object, deletes the key, and writes the whole object back as `state`. It sets `window_started_at` to this tick. It does not write `owner_channel`. If the walker advanced on this same tick, the database had already taken the next cell’s index and channel, set `delivered` and `delivered_at`, cleared `fired_criteria`, and sent that cell’s subject and body. The arm’s update puts the old index, the old `cellId`, and the old `delivered_at` back, and leaves `owner_channel` on the new cell. It then sends a second body for the owner the tick started with. `pickAuthoredContent` returns null while `override_this` is false, so that live subject is `Tower — attempt` plus the attempt number. The ladder reloads the split row. Rules resolved for the starting owner fail the channel test against the new owner, which is the reload claim 75 already used, so the ladder does not write the index a second time. The next tick loads the old index. The next cell is still due. The walker sends it again.

That is the rewind the handoff asked about. The first reading, that the seeded reactivation calendar would hit it, did not survive the order of the tick. The platform order is text, then email, then form. Form is a forward channel, and `acr-form` is `return_to_sequence_head`, so the seeded order never sets the key. A shorter order, or an `escalate_forward` from the last token, does set it, which is the cycle claims 72 and 73 already named. The email window is 86400 seconds, and the seeded day gaps are that same day. On the tick that window would elapse, the next day cell is due, the walker runs first, and the reloaded owner is no longer the one whose rule would have queued. The queue is not set between those cells. The worker interval defaults to 60000 milliseconds. A cell that becomes due while the key is still ahead is taken on an intervening tick. The rewind is the tick that is the first to see both the next offset and the key elapsed. The seeded templates do not line those two up before the last cell. The write is still what a templated attempt does when they do.

## The key rides forward, and the day still wins

While the key is still ahead of `now`, the tick runs the walker and then `continue`s. The ladder does not run. The arm does not clear the key. The walker’s next state spreads the loaded state, so the key rides onto the new cell. On the elapsed tick the loaded index is already that cell, `last_escalation` is `cell:` plus the cell id, and the cell was sent when it was entered. Writing that object back minus the key does not restore the cell the queue was sitting on. The live arm still sends, and it still moves `window_started_at`.

The queue is what sets `last_escalation` to the criteria id, and it does not change `cellIndex`. The walker is the later writer that sets `last_escalation` to a `cell:` value.
