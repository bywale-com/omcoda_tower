## What the first step stores

`enrollAndActuate` in `server/wire-service/cascade.ts` sets `live` from `shouldLiveSend(input.contactId)` and inserts `enrollment` with the caller’s payload, then `dryRun: !live`, `templateId`, `cellId`, and `campaignId`. It then inserts `active_attempts` at `status` `open`, with `state.delivered` true, `delivered_at`, `cellIndex` 0, and `attempt_n` 1. Only after both inserts, and only when `fireFirstStep` is not false, does it call `actuateChannelSend` and `writeEngagement`. The kind argument is `live ? "send_live" : "send_dry_run"`. The payload always includes `enrollmentId`, `attemptId`, `channel` (the owner), `templateId`, `cellId`, `cellIndex`, `subject`, `bodyText`, and `send`. `messageId` is copied only when `send.ok && !send.dryRun`. `reason` is copied only when `send.ok && send.dryRun`. The function returns `dryRun: !live` in every non-halt case. A deny does not change the enrollment flag and does not change the return.

`actuateChannelSend` can return a dry run before the dispatcher: no email and no live test address, no phone and no live test address, or a channel that is neither email nor text. Those are `ok: true` and `dryRun: true`. They are not the deny. `dispatchEmail` and `dispatchSms` call `consentAndHaltGate` and return that deny before the cohort short-circuit. A silenced contact is therefore `ok: false` even when `shouldLiveSend` is false, and this writer then files `send_dry_run` because `live` is false, with the subject and the body, and with no `reason`. A contact in the live cohort gets the same deny filed as `send_live`, with no `messageId`, with the copy present, and with `send.ok` false. The missing-Resend return is `{ ok: false, deny: "policy", detail: "RESEND_API_KEY missing", dryRun: false }`. It is reached only on the live path, and the cohort flag still labels it `send_live`. A provider failure is the same shape without that `dryRun` field. `DispatchResult` is the three shapes claim 21 already used. The purpose on this call is `input.purpose ?? "opt-in"`. `call_agent` passes `opt-in` or `cem` from the sequence class. The reactivation fallback passes `reactivation`. The kind does not read the purpose and does not read `detail`.

## How the reading changed

The first reading was that this write might be a different fact from the tick. A halt already stored never reaches it. Claim 20 had excluded the first step for that reason and had called it the start of an enrollment the enroll check allowed. The enrollment has already recorded `dryRun`. The step keys include an `enrollmentId` the tick writers do not all carry. It was possible to hear the cohort flag, or the mere existence of the enrollment, as the record, and to leave the kind on `shouldLiveSend`.

That reading lost once the gate’s order was put next to the kind. The deny returns before the cohort short-circuit, so the cohort flag and the result come apart. A non-live silence is filed as a dry run. A live-cohort silence, a missing key, and a provider failure are filed as a live send that has no `messageId`. The list title is the kind. The outcome line does not consult `payload.send`. The body is on the payload, so the inspector replays a message that did not leave. That is the false file claim 21 refused, on the same `DispatchResult`. The fact that a stored halt usually never arrives does not change the result when a deny does arrive, including a halt written between the two queries. Claim 20 had already read that ordering and left it as ordering.

The enrollment flag was the other place the two facts could have been collapsed. It is computed from `shouldLiveSend` and inserted before `actuateChannelSend` returns. The return echoes it. It does not echo `send.ok` or `send.dryRun`. The actuation report’s dry run is `SEND_MODE` and the cohort. The deny is the other shape. A live-cohort contact who is refused is still live-eligible. Writing `dryRun: true` onto the enrollment because the send failed would store the refusal as a dry run, which is the label claim 21 already refused, on a different table. The chronology the consultant reads is `engagement_records`. The flag stays the cohort posture. The row is the refusal.

Omitting the row on `ok: false` lost for the reason it lost on the wait arm. This step has no `window_fired` and no `cell_advanced`. The enrollment and the attempt are other tables. A hole does not say the first message was refused. A different kind, on the theory that silence and throughput are not the tick’s halt, lost because the branch is `send.ok` and claim 21 already put those details on `send_denied`. The step keys say which enrollment’s first step it was.

The allowed arms had to follow the same rule. The live code uses one expression for every result. Leaving `shouldLiveSend` in place for an allowed result would still file a missing-address dry run as `send_live` when the contact is in the cohort and the test address is unset, because `actuateChannelSend` returns `ok: true` and `dryRun: true` before the dispatcher, and the kind would still be the cohort flag. Claim 21 had already said the cell’s conjunction is not the label. The label is the result on all three arms.

The attempt’s `delivered: true` was the write that could have been reopened. It is set in the insert, before the send, the same class of pre-send write claim 20 left taken on the cell. The tags read that flag. They were not retuned. `hasInboundOverride` still does not read a send kind.

The callers were opened only far enough to see whether some other store records the deny. `handleEnrollmentCreate` returns both `dryRun` and `send`. `handleOnboardingFire`’s no-workflow loop counts `!result.dryRun` as `liveSends` and drops `send`. The reactivation fallback and `handleSequenceEnrollContacts` keep the enrollment id. `call_agent` pushes the enrollment id onto the node’s writes. `writeEngagement`’s id is not on the function’s return, so the walker cannot push it. None of those callers writes a second engagement row. The `liveSends` count is a reading of the cohort flag under a name that says send. Giving it a new formula would be specifying that onboarding response. It was left as a distinct obligation. The reactivation enroll itself was not specified.

Blocking the insert, so that a deny would have no first step to record, was considered and was not decided. The enroll check is halt. The send gate is the later call. The row is the record of a first step that ran.

## What was settled

The payload carries `enrollmentId`, `attemptId`, `channel`, `templateId`, `cellId`, `cellIndex`, and `send`. Subject, body, `messageId`, and `reason` stay off it. An allowed result is `send_live` or `send_dry_run` from the result, with the copy and with `messageId` or `reason`. `shouldLiveSend` is not the kind. `enrollment.payload.dryRun` stays `!shouldLiveSend`, and the return’s `dryRun` stays that boolean. The attempt stays open. `delivered` stays as the insert wrote it. A stored halt still produces no row. The consent select was not specified. No migration. No founder question. The words the licensee reads on the chronology were already separated by claim 21. This writer was the remaining caller that ignored the result.
