## What the session was trying to establish

Claim 17’s walk, when the firing names nobody, is this firm’s contacts, and `call_agent` enrolls each of them under the walk’s firm. The live check can still return true because some other firm stored a contact-scope halt for the same `contact_id`. The product either already treats a contact halt as a refusal inside the firm that wrote it, or the contact id is a person the halt follows into every firm that tries to enroll it. Which of those is true had to be read off how a contact id is scoped, what the halt row stores, and what a halt is already said to do. A halt that crosses firms is the kind of split that can belong to the founder, so the existing decisions had to be given a chance to settle it before that question was left open.

## Whether one contact id can sit in two firms

`contact_records.id` is `TEXT PRIMARY KEY` in `supabase/migrations/004_machine_tables.sql`. `firm_id` is required and is not part of the key. One id is one row, and that row names one firm. Migrations 014 and 015 add `import_batch_id` and `notes`. They do not change the key. `handleContactImport` and `executeAuditRun` both insert `ON CONFLICT (id) DO UPDATE`, and the update assigns email, phone, and name. It does not assign `firm_id`. A second firm that supplies an existing id does not gain a second book row and does not move the first. An import that omits an id mints `cr-` plus a uuid. The seed book in `supabase/seeds/002_machine_tables.sql` uses `cr-cedar-*` and `cr-harbor-*`. Those strings do not overlap. Email and phone have no unique constraint. The same person on two books is two ids, and a halt of one id does not mention the other.

That closed the reading in which “another firm’s contact” is a second book row with the same id. It did not close the gate. `halt_records.contact_id` is not a foreign key. A halt row can store this contact id with a `firm_id` that is not the book row’s firm. The live arm matches that row.

The pair keys changed the reading of what the product already does with one id across firms. `consent_records`, `reachability_verdicts`, `sequence_ready`, and `cohort_tiers` are keyed `(contact_id, firm_id)`. A second firm can hold its own consent or verdict for an id whose book row remains the first firm. Claim 15 already kept the firm on the consent re-read for that reason. Halt stores `firm_id NOT NULL` on every row. The firm-book reader uses it. The contact reader drops it. The column is not a new fact this session would have to invent. The reader is the part that does not use the fact the row already has.

## Where the live arm and the product pair agree, and where they do not

On the path claim 17 specified, the empty firing walks contacts of the firing firm, and the desk’s halt of such a client stores that firm. The live contact arm and a firm-scoped contact arm both block that enroll, and both allow it when the only contact halt is lifted or belongs to someone else. The arms diverge on a row whose `contact_id` equals the person being enrolled and whose `firm_id` is some other firm. That is the row the handoff meant. It is not a second copy of the person. The enroll firm’s board does not list it. Blocking on it would stop this firm’s insert for a refusal this firm’s desk does not show, and it would let this firm’s halt stop another firm’s insert of the same id.

The other divergence is a firing that already names an id whose book row is another firm. Claim 17 left that list alone. `call_agent` would stamp the walk’s firm on it. An unscoped contact arm would let the book firm’s halt stop that insert. A firm-scoped arm would not. Using the halt to catch that stamp would make this gate do the audience cut claim 17 refused to add, and it would still miss the same human under a second id. The import conflict is how such an id gets onto a firing: the second firm’s `ON CONFLICT` does not move `firm_id`, and the dispatch still passes the id. That update was not specified. It is recorded as distinct from this predicate.

## Alternatives, and why they lost

Leaving the contact arm on `contact_id` alone loses because that is the live query, the index, and the two readers claim 14 already declined to decide. The row stores the firm. The firm-book arm, the board list, the desk commit, and the pair keys already use a firm. An unscoped match is how a row the board does not show stops the insert.

Matching `contact_records.firm_id` instead of the enroll firm loses on the stamp claim 17 left in place. For a desk-written halt the two firms are the same. The gate would then be policing a foreign id on the walk, which is the audience question, and it would still not see a second id for the same person. The firm the run is acting as is the enroll firm.

Requiring both firms loses because the book row cannot sit in two firms, so the extra conjunct does not change a desk-written pair. It adds a `contact_records` read to a check the halt row already answers.

Joining another firm’s contact by email or phone loses because there is no such key. Two books are two ids. That join would be the platform-wide stop desk-13 sets the two scopes against. No person table was added.

Treating the kill-switch as a contact-id match loses because each commit is firm-book for one target firm and carries no contact. The firm-book arm is that control.

Dropping the contact arm and keeping only firm-book loses because This contact is the surgical scope inside the firm. A book halt of another firm is not how one client is refused.

Retuning `consentAndHaltGate` and `handleHaltIsContact` in this claim loses because they are the same shape and they are a further reader. The first-step send still runs after an enroll this predicate allows. They were named and not rewritten.

The cross-firm reading was the one that could have gone to the founder. A halt that followed the contact id would change whose license binds the motion, including across firms, and the leaves do not contain a sentence that says “a contact halt does not apply in another firm.” That missing sentence was not the stop. The id is not a cross-firm person. Per-firm state for one id is already how consent and the audit flags are keyed. The refusal already described is firm→client under this license. The board already shows this firm’s rows. The control that crosses firms already writes a firm-book row per firm. Those decisions pick the firm on the halt row. No founder question.

## What was settled

Another firm’s contact halt does not block this enroll. The contact arm of `isHaltBlockingNew` is an active row with `scope = 'contact'`, `contact_id` of the person being enrolled, and `firm_id` of the firm `enrollAndActuate` was given. The firm-book arm stays as it is. A lifted row does not block. The live contact arm still has no `firm_id`. No migration was written.
