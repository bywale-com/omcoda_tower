## What the handler actually does

`handleOnboardingFire` takes the session firm from `requireSessionFirm`. It reads `campaign_states` for that firm. A missing row, or a state other than `running`, returns `skipped` and does not dispatch and does not enroll. Past that, it loads `firm_sequence_binding` for sequence class `optin`, `is_default` descending, limit 1, and otherwise uses `tpl.optin_launch.v1`. It selects `contact_id` from `sequence_ready` where `firm_id` is that firm and `ready` is true. Claim 8 had already said the enroll reads the latest ready row and includes the contact once. The dispatch is `audit.completed` with payload `{ trigger: "campaign_state=running", onboarding: true }`, those contact ids, and no `writes`. When the returned list is empty, the function calls `enrollAndActuate` with that agent and the same id as the sequence, payload `{ trigger: "campaign_state=running" }`, purpose `opt-in`, and no `fireFirstStep`.

Inside `enrollAndActuate` a halt already stored returns before any insert. The handler pushes `{ id: "", dryRun: true, blocked: "halt" }` for that return. Past the halt, the omitted flag enters the first-step branch. The send is `actuateChannelSend` with purpose `opt-in`. Claim 23 denies that purpose when `silenced` is true or `status` is `silenced`, and it allows a missing row and `basis` `none`. The insert itself does not read the pair. The response counts `enrollments` as the length of the array, `dryRuns` as `result.dryRun`, and `liveSends` as `!result.dryRun`. It does not read `result.send`.

`wf-optin-launch` is seeded `draft`, with an enabled `audit.completed` trigger. A seeded firm does not take that graph, so the fallback is the path it takes once the campaign is `running`. `AuditContext.persistAuditRun` calls `fireOnboarding` only after a real audit whose `contacts` is greater than zero. The port type names `skipped`, `enrollments`, and `agentRef`. The caller discards the body. `standInMachineApi.fireOnboarding` returns zero enrollments and the platform id. It does not read the ready table or the consent table. It is not this path.

## Why silence stops the insert and a missing basis does not

The first reading was claim 43’s own refusal: do not copy the reactivation withhold onto an opt-in caller. That refusal was the missing-basis arm. It was not a finding that silence is allowed. `docs/register/how/contact-silence.md` says runners, send gates, and book readiness read the silenced state, and that the contact is not sequence-ready for new automatic motion. The leaf names the opt-in footer as one of the places the contact silences. `docs/register/how/operator-book-readiness.md` says enrollment is the autonomous entry into engagement, and that silenced contacts are excluded from automatic motion. `docs/register/system-map/ACTUATION-REPORT.md` says silence always blocks, and that an opt-in purpose may proceed without a prior basis. Those are two arms. The loop is the entry. Leaving the insert would open an attempt. Claim 20 keeps ticking it. Each later deny would be another send.

The silence arms deny `cem` the same way they deny `opt-in`. An open attempt for a silenced contact is not a refused message. It is new automatic motion after the pair has already refused the send. The same silence arms, applied before the call, are one rule. ## What the tick opened and did not settle

For a reactivation enroll, `cem` and `reactivation` are the same gate: both are not `opt-in`, so a missing basis denies either string. For this enroll they are not the same gate.
