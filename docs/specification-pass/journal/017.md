## What the session was trying to establish

A send that is refused for silence or for a missing consent is refused because of some row, or because no row was found. The live query can see every `consent_records` row for the contact. Claim 15 had already said the listener re-reads one pair, and had left the gate’s predicate unspecified because it had not asked whether one contact id can sit in two firms. Claim 18 later answered the book half of that question for halt, and said the same id can still carry a second firm’s consent. The halt of that other firm does not bind this firm’s enroll or this firm’s send. The consent query was the remaining reader in the same function that could still let the other firm’s row decide.

## What the select is aimed at

`consentAndHaltGate` takes `contactId`, `firmId`, and `purpose`. The firm-book arm matches an active `firm-book` halt for that `firmId` and can return before any contact is considered. When a contact is present, the consent query runs. `silenced` true, or `status` equal to `silenced`, returns `detail` `silenced`. When `purpose` is not `opt-in`, a missing row or `basis` `none` returns `detail` `consent missing`. The contact halt query runs only if those arms allow. `dispatchEmail` and `dispatchSms` return the deny before the cohort short-circuit. `dispatchEmailLive` and `dispatchSmsLive` call the gate again with the same firm.

The table was read next, because the query’s meaning depends on the key. `consent_records` is `PRIMARY KEY (contact_id, firm_id)` in `supabase/migrations/003_ct_wire_stores.sql`. There is no foreign key to `contact_records`. `contact_records.id` is the primary key, and `firm_id` is a required column that is not part of that key (`supabase/migrations/004_machine_tables.sql`). One contact id is one book row and one firm. Claim 18 had already said the same person on two books is two ids, and that a second firm can still hold a consent row for an id whose book row remains the first firm. This session did not need a new theory of the book. The pair is enough for two consent rows, and the live query does not say which of them `LIMIT 1` returns.

That is the same split as the halt. A silence stored under another firm can be the row that denies this firm’s send, including an opt-in, because the silence arm does not look at `purpose`. This firm’s own silence can be the row the query misses, and the send continues into the halt arm as if this firm had no silence. The other direction is an allow: another firm’s `express` basis can satisfy a purpose that is not `opt-in` when this firm has no row, or when this firm’s basis is `none`. Claim 22 would file either deny as `send_denied` without reading `detail`, so the chronology would not say which firm’s row it was. The file was not the question. The row was.

## What was considered and set aside

Leaving the live predicate was the first alternative. It is what the code does. It makes the deny depend on a row the sending firm’s seat does not show, and it can allow a non-opt-in send on another firm’s `express` basis. That is the halt split, on the table whose key already separates the firms.

Honoring any denying row for the contact, or any `express` row, was the stricter and the looser form of the same idea. Both apply another firm’s state to this firm’s message. Claim 18 had already refused a halt that followed the contact id into every firm. The same person on two books is two ids. This id’s second consent row is not a second person.

Ordering by `updated_at` and still omitting the firm would make the result determinate and would still cross firms. The newest write in the other firm would govern this firm’s send. Claim 15’s readers ask for the current row of the pair. Claim 7 and claim 8 had already refused “latest” as the name of the row this run is acting on.

Matching `contact_records.firm_id` instead of the firm on the call was claim 19’s rejected alternative for the halt, and it fails here for the same reason. The address lookup already uses the send’s firm. The book firm and the send firm differ when a firing names an id whose book row is another firm and the send is stamped with the walk’s firm. The book firm’s consent would then govern the walk’s send, or the walk’s silence would be ignored. Requiring both firms would turn the gate into the audience cut. The predicate stays on `consent_records`, and the firm is the one the send was given.

Joining another book by email or phone was refused under claim 18. Those columns are not a key. This session did not add a person table.

The stand-in was opened to see whether the product had already settled “one row per contact” somewhere the table had not. `standInConsentSilence` keeps one slot per `contactId`. `setConsent` and `silence` store `firmId` on that slot and replace whatever firm was there. `get` does not take a firm. `standInListUnsubscribe` writes the slot with the firm it was given. `standInSendGate` calls `get(input.contactId)` only when a contact is present, and then pushes `silence` or `consent`. The `decide` calls in `FirmOperationsBindModule.tsx` pass the firm and do not pass a contact, so that arm does not run on those calls. `standInSmsApi` also calls `get` when it has a contact, and its comment names CASL; it denies on `basis` `none` with no opt-in exemption. That comment is the regime silence. It was not used to choose the row. The map cannot hold two pairs. The table can. The map does not settle the select. It remains a different store.

`handleConsentGet` is the same contact-only `LIMIT 1`, returning `basis`, `silenced`, and `source`. The route is `GET /consent/:contactId`. `realConsentSilence.get` calls it with the contact id and no firm. That read was seen and was not specified. It is the same predicate on a route that does not send.

Assigning `status` on the silence upsert was considered only long enough to keep it out of the predicate. The arms the gate already has, applied to the firm’s row, name the deny without choosing a geography or a basis regime.

Changing claim 22’s kind when the deny is consent rather than halt was rejected because the writers branch on `send.ok` and do not read `detail`. Which row produced the deny is this claim. The file stays one kind.

## What was settled

The select returns the row whose `contact_id` is the contact and whose `firm_id` is the firm the gate was given. `LIMIT 1` stays. There is no `ORDER BY`, because the primary key is that one row. Another firm’s row does not deny and does not satisfy. A missing pair is the missing-row arm the function already has. The silence, basis, and purpose arms were not retuned. No migration. No founder question. The consequential choice was whose consent binds the send. The pair key, the firm already on the call, the seat, the firm→client leaves, and the halt claims had already answered it. The live query is what disagrees.
