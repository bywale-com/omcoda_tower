## What the three paths do

`tickOnce` loads `active_attempts` where `status` is `open`. It does not read `halt_records` and it does not call `isHaltBlockingNew`. For each open row it can send from three places, each through `actuateChannelSend` with `attempt.firm_id`, `attempt.contact_id`, and purpose `cem`.

The cell advance updates the cursor first. It sets the next cell, `delivered` true, `delivered_at`, writes a `workflow_run`, and writes `cell_advanced`. Then, if the new channel is email or text, it sends. `criteriaDue` treats `state.delivered` as the delivered condition, and `clockAnchor` prefers `delivered_at`. A later window can therefore treat the cell as delivered even when the send comes back denied.

The wait-until arm runs when `attempt_wait_until` is already due. It deletes that key and moves `window_started_at`. Then, if the owner is email or text, it sends. The return value of that send is discarded. The engagement written afterward is always `send_dry_run`, with no send object.

The escalation updates `owner_channel`, `fired_criteria`, and `state`, and writes a `workflow_run` and `window_fired`, before it sends. The send runs when `toChannel` is email or text and the queued next attempt is not still waiting. A branch that is still waiting does not send inside this function. The later wait arm is the send for that case. `fired_criteria[criteria.id]` returns early on a later tick, so a criteria id already written is not fired again. A send engagement is written only when `send.ok`. A deny writes neither `send_live` nor `send_dry_run` on this path.

`actuateChannelSend` calls `dispatchEmail` or `dispatchSms`. The comment on `dispatchEmail` says it is the gated send for the cascade and the worker, and that halt still denies. Both functions call `consentAndHaltGate` and return that deny before the cohort short-circuit. The live dispatchers call the gate again and return before Resend or Twilio. Claim 19’s contact arm is the firm on that call. The firm-book arm of the same function already requires the firm. The halt arm does not read purpose, so `cem` does not exempt the tick. A channel that is neither email nor text never reaches the function. A missing address with no live test fallback returns the dry-run claim 19 already left outside the gate.

The comment on the enroll check is the other half of the same H1 notes. It says a firm-book or contact halt blocks new enrollments and does not abort in-flight attempts. The tick never calls that function. The status write to `nullified` on this path is `hasInboundOverride`, once in `tickOnce` and once inside the escalation. Halt does not call it. This session did not retune that function. Whether a halt should change the inbound override is the interaction P1 parked.

Stopping because P1 once asked for a founder write also lost. H1 is the later lock, and the analysis index says it chooses suppression-only over the parked gap. What remains of P1 is the abort and the Engine 2 / live-override interaction. That is distinct from whether this message leaves.
