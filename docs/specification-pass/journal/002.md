# Journal 002

The session began from `docs/specification-pass/NEXT.md`, then the standing specification, then journal 001. The named move was one outbound message stamped for enrollment A, with enrollment B newer and still open, followed from `webhooks.ts` through `onCompletionWrite` and `objectiveSatisfiedBy`, to decide whether A fails to advance. That either locked claim 3 against the send or revised it. The audit primary key was left alone until the click was settled. Failure (packet 023) and lineage (Automations law 29) were not reopened. No product code was changed.

## What the session was trying to establish

Journal 001 had already decided that a completion belongs to the pursuit named on the stamp, and it had seen that the click webhook reads `firm_id` and `contact_id` and then calls `onCompletionWrite`. What it had not done was sit on a message that actually carried `enrollment_id` and `campaign_objective_id` and follow that row into the matcher. The open question was whether the stamp is written at all. If `actuateChannelSend` never persisted those columns, claim 3’s sentence that a click’s identity is the `outbound_messages` row was ahead of the code. If the columns were written and the click then ignored them, the false negative was confirmed and the claim locked. If the click already advanced the enrollment named on the row, the earlier claim was wrong.

## Where an outbound message is written

`actuateChannelSend` in `server/wire-service/cascade.ts` does not insert `outbound_messages`. It resolves the contact’s email or phone and calls `dispatchEmail` or `dispatchSms`, forwarding `enrollmentId`, `campaignId`, `campaignObjectiveId`, and `attemptId`.

`dispatchEmail` and `dispatchSms` in `server/wire-service/dispatchSend.ts` run the consent and halt gate, then return `{ dryRun: true }` when `shouldLiveSend` is false. That return is before any insert. `server/wire-service/sendMode.ts` makes the miss the default: `SEND_MODE` other than `live` is dry-run, and live still requires the contact in `SEND_TEST_COHORT`. A dry-run sequence send therefore has no row, and no Resend id a click could name. The walk is about a message that exists, so it is the live insert.

`dispatchEmailLive` and `dispatchSmsLive` are the inserts. Both write `enrollment_id`, `campaign_id`, `campaign_objective_id`, and `attempt_id`, taking null when the caller passed nothing. The email branch stores Resend `data.id` as `provider_message_id`. The SMS branch stores the Twilio sid the same way.

The sequence callers do pass the stamp. `enrollAndActuate` passes the enrollment id it just inserted, `firstCampaignId` for the sequence, and `campaignObjectiveIdForCampaign` of that campaign, plus the new attempt id. The later sends — the channel change inside the tick, `advanceTemplateCellIfDue`, and the send after a wait — call `pursuitStampForEnrollment`. That function reads `enrollment.campaign_id` for the attempt’s enrollment and then the objective id for that campaign (`SELECT id FROM campaign_objective WHERE campaign_id=$1 LIMIT 1`). `server/wire-service/send.ts` `handleCemSend` and `handleSmsSend` call the same dispatch functions with no enrollment and no objective. Those rows are the outside-a-sequence sends packet 022 already said must match nothing. They are not the message under test.

So the stamp is persisted, on the live sequence path, by `dispatchEmailLive` and `dispatchSmsLive`. Claim 3’s identity sentence is not ahead of the writer.

## The click, with A and B both still on a campaign

The message M used for the walk has `enrollment_id = A`, `campaign_objective_id = ObjA`, and `provider_message_id = P`. B has a later `enrolled_at` and `campaign_id` still set. That is the row the completion query will prefer. “Still open” here means that predicate, because `onCompletionWrite` ignores an enrollment whose `campaign_id` is null.

`handleResendWebhook` is the only click ingress that calls `onCompletionWrite`. The event class `clicked` comes from `email.clicked`. The handler selects `firm_id, contact_id` from `outbound_messages` where `provider_message_id` equals `event.data.email_id`. It does not select `enrollment_id` or `campaign_objective_id`. It inserts `messaging_events` with `message_id = P`, `event_class = 'clicked'`, and that contact, then calls `onCompletionWrite` with firm, contact, table `messaging_events`, and the new event id. The join the rest of the code assumes is that same pair: the insert stored `data.id`, the webhook looks up `email_id`, and `objectiveSatisfiedBy` compares `messaging_events.message_id` to `provider_message_id`. No SMS path calls `onCompletionWrite`. This lock is the email click.

`onCompletionWrite` selects one enrollment: this firm, this contact, `campaign_id` not null, ordered by `enrolled_at` descending, limit 1. That is B. It loads B’s objective. If `completion_table` is not `messaging_events`, it returns. A is never loaded. If B’s objective is a click, `objectiveSatisfiedBy` runs. Its click query does read the stamp columns. It reads them as predicates on the enrollment it was given. The preferred arm is `campaign_objective_id` equal to B’s objective. The other arm applies only when `campaign_objective_id` is null, and then only when `enrollment_id` is B and `created_at` is at least B’s `enrolled_at`. M was stamped, so the second arm does not apply. When ObjA and B’s objective differ, the query misses, `onCompletionWrite` returns, and nobody advances. When the ids are equal, the query hits, and `advanceEnrollmentCampaign` is called with B. The event id passed into `onCompletionWrite` is not a filter on that query. It is copied onto the `objective_met` engagement only after the match succeeds.

A is not an argument on this path. The click does not advance A.

## What that did to the earlier sentence

The first reading of the SQL looked like the false negative journal 001 described, and that reading holds when the objectives differ. Escalation to another agent is that shape whenever the new sequence’s current objective is a different id, or lives on `fact_writebacks` or `meeting_booked`. The completion-table check returns before the click query in the latter case. A is not considered.

The equal-id case is the same query, and it changes the outcome for B. `campaign_objective` is `UNIQUE (campaign_id)` in `supabase/migrations/010_sequence_campaign_housing.sql`. `enrollAndActuate` inserts a new enrollment and sets `campaign_id` to `firstCampaignId`. Two enrollments of one sequence therefore share one objective row. Claim 2 already established that the second insert is allowed. When B sits on that same campaign, M’s `campaign_objective_id` equals B’s objective, the preferred arm matches, and the click advances B. A still does not advance on the click. The earlier sentence is the different-objective case. It stays in the specification, with this case beside it. The standing rule did not change: the enrollment named on the send is the one that advances, and only while its current campaign still asks for that objective.

## The tick is why “fails on the click” is not “never advances”

`tickOnce` walks `active_attempts` in status `open` and, when the attempt has an `enrollment_id`, calls `advanceEnrollmentCampaign` with that id. That function loads the enrollment by primary key and only then calls `objectiveSatisfiedBy`. For A’s own attempt, the click query is given A and ObjA, and M matches the preferred arm. A later tick can advance A while that attempt remains open. Packet 022 §2.4 already called the tick the catch-up and the write the path that still runs after spending has stopped. Once A’s attempt is not `open`, the tick no longer loads A. The click has not advanced A either. That is when the miss sticks.

The same predicate creates the other half of the equal-id case. `enrollment_id` is consulted only when `campaign_objective_id` is null. A tick that still finds B on the campaign ObjA belongs to also matches M, so B advances from a send that named A. The click and the tick can both do that, depending on which one runs while B’s cursor is still that campaign. After B’s cursor has moved, `advanceEnrollmentCampaign` loads the new campaign’s objective, so a second call does not re-apply ObjA. The latch is intact. The attribution on the first call is not.

## The alternative that was not enough

One fix would be to change only the select inside `onCompletionWrite`: load M by `provider_message_id`, and pass M’s `enrollment_id` through. The webhook would then advance A. The tick would still call `advanceEnrollmentCampaign` for every open attempt, and any of those enrollments still on ObjA’s campaign would match M, because the predicate treats the objective id as sufficient. That alternative was rejected.

Refusing a second enrollment on the same campaign would also make the predicate safe. Claim 2 already rejected that. `enrollAndActuate` inserts, and the face enrolls per sequence.

The predicate that satisfies the standing rule is both columns. A stamped click matches enrollment E only when `outbound_messages.enrollment_id = E` and `campaign_objective_id` equals the objective of E’s current campaign. Packet 022’s fallback stays for rows whose objective id is null: `enrollment_id = E` and `created_at >= E.enrolled_at`. The click entry loads M and advances that enrollment. It does not choose the newest enrollment first. No founder question turned up. Packet 022 already said the stamp is the identity and that a missing stamp matches nothing. Claim 2 already said a second enrollment exists. The unique objective per campaign is already in the migration. Those three decide the predicate.

Claim 3 locks against the send. The form path and the meeting path were not re-walked.

## The readers under claim 8

The click was settled with the session still open, so the queries named under claim 8 were read. The grain was not changed, and the tree was not searched for further readers.

`handleContactRecordsList` left-joins `reachability_verdicts` and `sequence_ready` on `contact_id` and `firm_id`. That is the contact’s current verdict and current ready flag. `handleOnboardingFire` selects `contact_id FROM sequence_ready WHERE firm_id=$1 AND ready=true` and enrolls those contacts. That is who is ready now. `executeGet`, for module `contacts`, selects both tables by `contact_id` only and adds the pointers to the Get’s writes. That is the current row for the people the Get selected. The select does not constrain `firm_id`. That was seen and left. Firm isolation is outside this pass, and it is not the grain.

Those three are the “latest row per contact” readers. The earlier sentence that put every listed reader in that basket does not survive the other two queries.

`eventTest.ts` `door1`, for `audit.completed`, takes the newest `audit_runs` row with `status='complete'` (`ORDER BY started_at DESC LIMIT 1`), then verdicts whose `details->>'auditRunId'` equals that id, then `sequence_ready` for those contacts with no run column in the predicate. The file header calls door 1 the live instance. This is the newest run’s specimen. It is not the enroll gate, and it is not a page for a past run. After the grain change it should read that newest run’s own per-person rows.

`handleAuditRunGet` was in `machine.ts` next to the contact list. It was not in the original list. It loads `audit_runs` by the id on the path, then verdicts where `details->>'auditRunId'` equals that id, and left-joins `sequence_ready` on contact and firm only. `auditRun.ts` writes `details` as `{ auditRunId, rationale }` and upserts on `(contact_id, firm_id)`. A later audit replaces `auditRunId`, and the older run’s page loses the contact. The ready value on that response is whoever is ready now. The query is trying to answer what that run wrote. “Latest row per contact” would be the wrong follow on that page.

`loadWriteRow` was already described in claim 8 as the re-read that ignores the pointer id. It was not reclassified.
