## What the session was trying to establish

## The contact branch, and the row it inserts

`handleHaltCommit` reads `consultantId`, an optional `contactId`, `firmId`, `scope` of `contact` or `firm-book`, and an optional `reason`. It builds `haltId` with the file’s `id` function: the prefix, a hyphen, `Date.now()`, a hyphen, and `Math.random().toString(36).slice(2, 8)`. It inserts `halt_records` with that id, `consultant_id`, `contact_id` (`body.contactId` or null), `firm_id`, `scope`, `reason` or null, and `halted_at`. `lifted_at` stays null. Then it inserts `audit_events`. Then, only when `scope` is `contact`, it calls `dispatchEventToWorkflows` with `eventName: "halt_records"`, `firmId: body.firmId`, `payload: { haltId, contactId: body.contactId ?? null }`, and `contactIds` of that one contact when `body.contactId` is set. There is no `writes`.

That is one insert and one dispatch on the contact path. The id in hand is `haltId`, and it is the value the insert stored.

`supabase/migrations/003_ct_wire_stores.sql` gives `halt_records` `id TEXT PRIMARY KEY`. `contact_id` is nullable. `scope` is constrained to `contact` or `firm-book`. There is no unique constraint on an active contact halt. Two commits for one person are two primary keys. The partial indexes are active-row scans: firm-wide where `lifted_at` is null, and contact-scope where `lifted_at` is null. They are not the key.

`event_write_set` version 1, in `supabase/migrations/017_event_test_contract.sql`, names `halt_records` at ord 0 and names nothing else. The live contact insert writes that table. It does not skip it.

The first reading, from journal 007, was one missing array of one id. That part held. The write-set, the primary key, and the variable the insert already uses settle the pointer the same way claim 13 settled `cfail-`. `writesFromPayload` returns when `payload.writes` is an array and does not read `haltId`. With `writes` present it does not build a `contact_records` pointer from a contact list. This payload has no `contact_ids` array inside it. The person list stays the separate argument.

## Who hears it, and why the matcher case is not a hole

The client copy does the same. The compare against `local_ref` runs only when `local_ref` is set. A trigger with no `local_ref` still matches. A trigger that stored a `local_ref` does not, because null is not that string.

That looked, for a moment, like claim 13: a matcher asking for a key the payload does not carry. It is not that. ## The firm-book branch

The same handler, when `scope` is `firm-book`, first sets `lifted_at` on every other active firm-book row for that firm, using this commit’s `halted_at`. Then it inserts the new row with `contact_id` null and scope `firm-book`. Then it inserts `audit_events` with kind `halt.firm-book`, subject type `firm`, and subject id the firm. Then it returns the record. It does not call `dispatchEventToWorkflows`.

The first temptation was to call that an omission, because the write-set does not mention scope, the specimen includes a book row, and door 1 returns both scopes. The product copy says otherwise, and it says it on the control that performs the write.

`HaltOutreachModal` labels Firm book as stopping automatic firm→client sends across the book, and This contact as stopping automatic sends for this contact only. `confirmHalt` maps the book control to `scope: "firm-book"` and omits `contactId`. `FounderAgencyControlsModule` commits the same scope, one call per target firm, with no contact. Its copy says the write suppresses new enrollments and new sends and leaves in-flight attempts alone. Fleet-wide and selected tenancies choose which firms get a row. They do not choose a contact.

The runners already honor that row without a workflow. `consentAndHaltGate` in `dispatchSend.ts` denies a send when an active firm-book row exists for the firm, and the comment says that block applies even with no contact id. `enrollAndActuate` calls `isHaltBlockingNew` and returns `blocked: "halt"` before inserting an enrollment. The comment says a firm-book or contact halt blocks new enrollments and does not abort in-flight attempts. `handleHaltIsFirmBook` is the same active-row check. `docs/register/how/consultant-governance.md` leaf 1.2 and `docs/register/how/operator-founder-controls.md` leaf 1.2 name those readers: runners and send gates. They do not name an automation that starts because the book was halted.

Dispatching the branch would start every subscribed `halt_records` workflow with no `contactIds`. The every-firm audience would then load the firm’s contacts. That is the empty-list walk this session was told not to specify, pointed at a suppression. A fleet kill-switch would do it once per firm. The handler already withholds the call. The book specimen is a test body of the table. It is not a live firing. The branch stays the gate.

## Alternatives, and why they lost

Mapping `haltId` inside `writesFromPayload` loses because claim 7 refused a second channel, the function already returns on `writes`, and it never reads that key. The caller holds the id the insert stored.

Leaving the id on the scalar for the If loses for the reason claim 7 already gave. The pick is `mappedWrites` and `loadWriteField`.

Selecting the newest active halt loses for the reason claim 7 and claim 10 already gave. Door 1’s limit of ten is another reader. The gate’s `LIMIT 1` has no `ORDER BY`. It answers whether any active row exists. Two contact commits are two primary keys.

Using `contact_id` as the pointer id loses because the primary key is `id`. The gate looks up the person. A lookup by the contact id misses the row.

Adding a matcher case, or hoisting `scope` as an instance axis, loses because A26 and the primitives list do not offer Halt. There is no selected value for the compare to miss. `scope` on this firing is a column, and it is `contact`. A book-versus-contact control would be a new axis, and the book branch does not dispatch.

Dispatching the firm-book branch with the same array loses because the desk already defines that write as the gate, the handler already omits the call, and a dispatch with no contact would run the empty-list walk against the suppression, including a kill-switch that writes one row per firm. The specimen’s book body is not that firing.

Adding `audit_events` loses because the write-set names `halt_records` and the audit id is not kept. The halt id is already inside the audit jsonb.

Adding the lifted book rows loses because that update is the other branch. The contact path does not lift earlier contact halts.

Adding `contact_records` loses because the write-set does not name it and the separate `contactIds` argument is the person list.

Adding the table to `PERSON_WRITE_TABLES` loses because this firing has one pointer, the pointer carries `contact_id` when the column is a string, and the `halt-` id is not a person.

Loading by the audit pair, by the latest row for the contact, or with `lifted_at` null, loses because the primary key is `id`. The partial indexes are the gate. A lift updates this row, and the re-read has to see `lifted_at`.

Dropping `haltId` and `contactId` loses because they are already on the payload, and `contactId` is the contact-axis key. Adding `scope`, `reason`, `consultant_id`, or the specimen’s display names as root scalars loses because the matcher does not read them and the row already holds the columns the insert writes.

Copying the row, or putting `firm_id` on the pointer, loses for the reasons claim 8 and claim 10 already gave. Requiring `INSERT … RETURNING` loses because `haltId` is already the stored id. Adding Halt to the A26 list loses because the named list and the primitives table already exclude it. The pointer is for the dispatch the handler already performs.

No founder question. The write-set chose the table. The primary key chose the pointer id. The missing matcher case is the absence of an instance axis. The firm halt and the kill-switch stay the gate the desk already describes. A listener that is already subscribed starts from this insert’s `halt-` id. A later lift of that same id is visible on the re-read.
