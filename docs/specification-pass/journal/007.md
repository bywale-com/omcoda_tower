## What the session was trying to establish

Claim 12 had left this dispatch as the next site: one `cfail-` id returned, a payload with no `writes`, a write-set of one table, and a matcher that asks for a key the payload does not have. What it had not done was say which inserted row the listening run points at, or whether that matcher, the insert, and the write-set can be true at the same time. Two ways of naming the id can both be technically sound and still disagree about whether a trigger the operator bound to one campaign ever starts, and about whether the attempt or the enrollment is the row the listener reads.

## The branch that fires, and the row it inserts

`escalateAttemptWindow` in `server/wire-service/cascade.ts` is the only caller. The failure dispatch sits in the `!toChannel` branch. Earlier in the same function, a missing forward channel and a campaign id can still queue another attempt, and that path sets `toChannel`, so the failure branch does not run. When the branch does run, it reads the attempt’s enrollment again (`sequence_id`, `campaign_id`), calls `recordCampaignFailure`, and dispatches.

`recordCampaignFailure` in `server/wire-service/campaignHousing.ts` builds `cfail-` plus a uuid, inserts `campaign_failure` with that id, and returns it. The other columns are `firm_id`, `contact_id`, `campaign_id`, `sequence_id`, and `payload`. On this path the contact is the attempt’s contact. The campaign and the sequence are that second enrollment read, or null when there is no enrollment. The jsonb is `{ attemptId: attempt.id, criteriaId, setValue }`. The same transaction marks the attempt `exhausted` while it is still `open`, storing `campaign_failure_id` in `state`, and marks the enrollment `pursuit_state='exhausted'`. It does not write `enrollment.campaign_id`. The dispatch then sends `payload: { campaignFailureId: failId, attemptId: attempt.id }`, `contactIds` of that one contact, and no `writes`.

That is one insert and one dispatch. Packet 023 already required one failure row and one dispatch per exhaustion. This session used that only as the cardinality of the pointer. It did not reopen the spending stop.

`supabase/migrations/010_sequence_campaign_housing.sql` gives `campaign_failure` `id TEXT PRIMARY KEY`. `campaign_id` references `campaign` and is nullable. It is not the key. The version 1 specimen puts two rows on the same campaign, Alvarez `cfail-harbor-alvarez-email-3` and Tanaka `cfail-harbor-tanaka-sms-2`, both `camp.optin.harbor.v1`. Two failures of one campaign are two primary keys.

`event_write_set` version 1, in `supabase/migrations/017_event_test_contract.sql`, names `campaign_failure` at ord 0 and names nothing else. The live insert writes that table. It does not skip it.

Which enrollment a listener would load, when two enrollments share the contact and the campaign, was left as distinct work. Claims 2 and 3 already say that pair can exist. The first reading, from journal 006, was one missing array of one id. That part held. The id in hand is the return value, and it is the primary key.

## The matcher, and why the column was not yet the axis

`localRefFromPayload("campaign_failure")` in `workflowWalk.ts` returns `campaign_id` or `campaignId` from the payload. `triggerLocalRefFromPayload` in `src/app/data/automationTriggerSelect.ts` is the same pair of keys. `localAxesMatch` compares that string to `local_ref` only when `local_ref` is set. The live payload has neither key, so the compare is null against the stored campaign, and a local trigger that selected a campaign does not start. An unset `local_ref` skips the compare.

Packet 022 §1 is why this event is local at all: the axis is `campaign_failure.campaign_id`, a column on the row, and the matcher tests only the axes the operator specified. The insert stores that column. The dispatch does not copy it. The write-set, the insert, and the matcher therefore do not meet in the running code. They are not three incompatible requirements. The caller still holds the value it just wrote, on the second enrollment read, which is the argument `recordCampaignFailure` received as `campaignId`.

The earlier peek in the same function, the `campaignId` used to decide whether another attempt is queued, is a different read. The failure branch queries the enrollment again after the window’s other writes. The column is the later value. The scalar has to be that later value. Using the peek would name a campaign the row might not have stored.

The operator’s control stores the same kind of string the column holds. `TRIGGER_SELECT_EVENTS` gives this event a firm layer and a campaign layer, labelled Every campaign and Select campaign. `AntAutomationWorkbench` fills Select campaign from `listSequenceHousing`, `value: camp.id`, `label: camp.name`. `TriggerSelectModal` writes that value to `local_ref`, and Every campaign clears `local_ref` while leaving `grain` local. A selected campaign is `campaign.id`. The failure row’s `campaign_id` is `enrollment.campaign_id`, which is that id. Packet 023 keeps the cursor on that campaign when the pursuit exhausts, so the column at exhaustion is the campaign the pursuit was still on.

The other axes did not need a new key, which narrowed the break. `localAxesMatch` takes `firm_id` or `firmId` from the payload and otherwise uses `opts.firmId`. This dispatch already passes `firmId: attempt.firm_id`. The contact compare uses `payload.contact_id` or, when that is absent, `opts.contactIds`. This event’s layers do not include a contact axis, and picking the event clears `localContactIds`. The separate `contactIds` argument is the one contact. The hole is the campaign axis alone.

A null column is a real call. No enrollment, or an enrollment whose `campaign_id` is null, still inserts and still dispatches. `payloadString` ignores a null. A selected campaign does not match. Every campaign has no `local_ref`, so it still matches. That is the matcher that is already there. It is not a new rule about null.

`dispatchEventToWorkflows` runs `localAxesMatch` on the dispatch payload, then copies that payload onto the trigger and sets `anyPass: true`. The scalar has to be on the object passed in. The walker’s copy is too late for the match. Claim 7’s refusal of `anyPass` was not recut. `writesFromPayload` still returns on `payload.writes` and does not read `campaignFailureId`. With `writes` present it does not build a contact pointer from a contact list. This payload has no `contact_ids` array inside it. The person list stays the separate argument.

`loadWriteRow` falls through and returns null for `campaign_failure`. Claim 10 already requires `WHERE id = pointer.id` for a table whose primary key is `id`, with no firm predicate, no contact predicate, and no “latest”. Applying that predicate is not a new load. The function was not retuned. The table is not in `PERSON_WRITE_TABLES`. This firing has one pointer, so the set was not retuned either. The pointer still carries `contact_id`, because `personIdsFromWrites` uses that field when it is set, and the `cfail-` id is not a person.

Door 1 in `eventTest.ts` selects the newest ten `campaign_failure` rows for the firm. That is the specimen reader. The version 1 bodies also put `attemptN`, `channel`, `to`, `subject`, `reason`, and `lastAttemptAt` inside `payload`. The live insert stores `attemptId`, `criteriaId`, and `setValue` only. A later node that loads this firing’s row sees the live jsonb. The specimen was not retuned, and the insert’s jsonb was not enriched. `sequence_id` stays a column of that row. It was not added to the payload. The matcher does not read it.

## Alternatives, and why they lost

Mapping `campaignFailureId` inside `writesFromPayload` loses because claim 7 refused a second channel, the function already returns on `writes`, and it never reads that key. The caller holds the id the insert stored.

Leaving the id on the scalar for the If loses for the reason claim 7 already gave. The pick is `mappedWrites` and `loadWriteField`.

Selecting the newest failure loses for the reason claim 7 and claim 10 already gave. Door 1’s limit of ten is another reader. The seed row `cfail-harbor-4-exhausted` is another row.

Pointing at the exhausted attempt, or at the enrollment, loses because the write-set names `campaign_failure` and packet 023 already assigned those updates to the spending stop. The attempt id is a field of the failure row. The enrollment id is not on that row.

Using `campaign_id` as the pointer id loses because the primary key is `id`. The specimen pair shares a campaign and does not share an id. A lookup by the campaign id misses the row. The operator’s `local_ref` is the campaign, which is the axis, not the handle.

Changing the matcher to load the row, and omitting the scalar, loses because both copies of the matcher already read the payload, packet 022 §2.5 put the objective axis on the payload in that same function, and this event’s case already names `campaign_id`. The caller has the column. A load would be a second mechanism and would still need the id. The operator’s experience, a selected campaign matching this failure, is the compare that control already stores.

Putting `campaign_id` only on the `writes` element loses because `writesFromPayload` keeps `table`, `id`, and `contact_id`, and the matcher reads the root.

Adding root `firm_id` or root `contact_id` loses because those axes already fall back to `opts.firmId` and `opts.contactIds`. The campaign axis has no such fallback.

Dropping `campaignFailureId` and `attemptId` loses because they are already on the payload, the same way claim 11 kept `writebackId` and `meetingId`. Dropping `campaign_id` would make Select campaign miss. The two existing scalars stay. They are not the handle.

Adding `sequence_id`, or hoisting `criteriaId` and `setValue`, or copying the specimen’s `reason` and `channel` onto the root, loses because the matcher does not read them and the row already holds the ones the insert writes.

Adding the window engagement or the tick run loses because the write-set does not name them and they are written for windows that do not dispatch this event.

Treating the two specimen bodies as one firing’s two pointers loses because the live branch inserts one row and dispatches once. That is not the eligibility loop.

Loading by the audit pair, or by the latest row for the contact, loses because the primary key is `id`. The index on `(firm_id, contact_id)` is not the handle.

Copying the row, or putting `firm_id` on the pointer, loses for the reasons claim 8 and claim 10 already gave.

No founder question. The write-set chose the table. The primary key chose the pointer id. The matcher and Select campaign chose `campaign_id`, and the insert already stores that column. Putting the column on the payload is how that matcher already works. A listener on one campaign starts from this firing’s `cfail-` row when the column equals the campaign the operator selected. A listener that left the axis unset starts from that same row.
