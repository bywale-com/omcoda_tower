## What the session was trying to establish

Claim 15 had just specified a current row that has no `id` column. The consent pointer puts the contact id in both fields and takes the firm from the walk, because the primary key is `(contact_id, firm_id)` and `RunWrite` has no firm field. The firm firing looked, from the handoff alone, as if it might be the same shape: one row, a later call updates it, the walk already knows the firm. It also looked as if it might be claim 10, because the handoff said the upsert is on the firm id, and a table with an `id` primary key loads `WHERE id = pointer.id`. Those two shapes put different strings on the pointer, and one of them would treat a firm as a person. Which one the product already requires had to be read off the table, the writers, and what a listener is supposed to open. A missing `writes` array was the channel. It was not the choice.

## The provision handler, and the row it upserts

`handleMachineProvision` reads `firmName` and `email`, and it accepts optional `firmId`, `website`, and `role`. The firm string is the body’s `firmId` trimmed, or `randomUUID()` when the body omits one. The comment on the handler says that one id binds the session, `ct_firms`, and the machine. It inserts `firms` and, on conflict, updates the name. It inserts `ct_firms` with that id, the trimmed name, posture `Idle`, and `updated_at` now. On conflict of `id` it sets `name` and `updated_at`. It does not assign `posture` or the pool columns. It inserts `campaign_states` at `armed-for-activation`, and the conflict clause sets that state again. It then inserts or rebinds `users` for the email, and on success it mints an access link. The user block is the only one in a try/catch. A failure there still continues. Then it calls `dispatchEventToWorkflows` with `eventName: "ct_firms"`, `firmId` set to that same string, and `payload: { firmId, firmName, email }`. There is no `writes`. There is no `contactIds`. After the dispatch it appends a firm audit of kind `firm.provisioned`. The route returns the firm id, the name, the email, the website, the role, and the login path. The `ct_firms` statement has no `RETURNING`.

`supabase/migrations/003_ct_wire_stores.sql` gives `ct_firms` `id TEXT PRIMARY KEY`. The columns are `id`, `name`, `posture`, `pool_slug`, `pool_domain`, `sending_identity_id`, `created_at`, and `updated_at`. `posture` is constrained to `Idle`, `Armed`, or `Active`, and it defaults to `Idle`. There is no `contact_id` and no `email`. Migration 001’s `firms` and `users` are a different pair of tables. `campaign_states` in migration 004 is keyed by `firm_id`, not by a row inside `ct_firms`.

`event_write_set` version 1 names `ct_firms` at ord 0 and names nothing else. The live statement writes that table. It does not skip it. The version 1 specimen is one body, Harbor, `id` `firm-standin-harbor`, posture `Armed`, with pool columns and `consultant_name` and `consultant_email`. It has an `id`. It has no `contact_id`.

The first reading, from the missing array and from claim 15, was that a current row with no separate id would put the firm in both pointer fields, or would leave the row off the pointer because the walk already holds the firm. The column list ended that reading. The primary key is a column named `id`. The handler already has the string. `writesFromPayload` keeps an element that has a string `table` and a string `id`, and it allows `contact_id` to be absent.

## One current row, and why it is not the consent pair

The next question was whether a later provision destroys a fact the listener has to keep. That is why claim 8 stopped using one upsert as “what this run wrote,” and why claim 15 did not: the consent readers ask for the current state, and a later write is that state changing. The firm writers were read. `handleMachineProvision` upserts on `id`. A second call that passes the same id updates `name` and `updated_at`. A call that omits `firmId` mints a new uuid and inserts a new row. There is no second row for one id. `handlePoolAllocate` upserts the same id and sets the three pool columns. It does not dispatch. Seed rows in `supabase/seeds/002_machine_tables.sql` and migration 013 set posture, including `Active`, and their conflict clauses assign posture. No handler under `server/wire-service` assigns `ct_firms.posture` after the provision insert.

The readers match one current row. Door 1 loads `SELECT * FROM ct_firms WHERE id = $1 LIMIT 1`. `executeGet` for the firms module returns `{ table: "ct_firms", id }` with no `contact_id`, and the client preview in `automationGet.ts` does the same. `projectSeat` reads `id` and `name` by that id. `operatorPanes.ts` checks the row by id. None of those queries name an earlier name after a later update.

The faces say the same thing. `docs/register/PRIMITIVES.md` lists “A firm was created / provisioned” with Global “All new firms” and Local “—”. It says a person-row splits people and a run-row is the artifact, and that after a node the next step points at the writes that run made. It also says the firm is already there, and the listener does the inside. `docs/register/how/operator-provision.md` says the commit writes tenancy and user state that Login reads. That is the current firm. `appendFirmAudit`’s own comment calls the audit append history, not a second boolean. That history is `audit_events`. The write-set does not name it. Claim 8’s split existed because the product asks two questions of the audit tables. Nothing opened here asks what an earlier provision stored after a later write to the same id, as a fact separate from the firm as it is now. A history of `ct_firms` rows would be the shadow copy claim 8 refused, and it would fight the primary key the handler upserts.

That settled the grain. It did not copy claim 15’s pointer. Consent has no `id` column, so the pointer’s `id` had to be the contact, and the firm half stayed on the walk. The firm table’s `id` is the firm. Door 1’s `writeId` already returns `body.id`. The Get already points at that id and leaves `contact_id` off. Putting the firm id in `contact_id` as well would make `personIdsFromWrites` treat the firm as a person, because that function returns `contact_id` whenever it is a string, before it looks at `PERSON_WRITE_TABLES`. The consent shape and this shape are both “one current row, a later write is visible.” They put different strings on the pointer because the keys are different.

## Where the id sits on the pointer

The dispatch payload therefore gains one element: `table` `ct_firms`, `id` the firm string the upsert used. No `contact_id`. The array follows the write-set. There is one table and one upsert, so there is one pointer.

The function was not retuned. It still has no branch and still returns null. Applying that predicate does not revise claim 10, and it does not revise claim 15. `firmId`, `firmName`, and `email` stay on the payload. `firmId` is the firm-axis key, and it is what `localRefFromPayload` reads. `firmName` is the name this call wrote. The columns a later node sees on the firm row are the ones the upsert leaves: on an insert, `name` this call’s `firmName`, `posture` `Idle`, pool columns null; on a conflict, `name` and `updated_at` from this call, and the previous posture and pool columns. The specimen’s consultant name and email are not stored. Door 1 was not retuned.

`dispatchEventToWorkflows` still copies the payload and still sets `anyPass: true`. Claim 7’s refusal of that flag was not recut. `writes` has to be on the object passed in. The HTTP body is not the dispatch. There is no `RETURNING`. The stand-in was not a second dispatcher of this event name. The only `eventName: "ct_firms"` call is this handler.

## Alternatives, and why they lost

Claim 15’s pair loses because this table has an `id` column and that column is the whole key. There is no contact to put in either field. The walk already holds the firm, and here the firm is the key, so the pointer’s `id` is the firm id rather than “the other half.”

Putting the firm id in `contact_id` as well loses because that field is the person. `personIdsFromWrites` would split on it. The firms Get already omits it.

Leaving the row off the handle, for the If to read `firmId` on the payload, loses for the reason claim 7 already gave. The walk’s firm is the tenancy of the run. The pointer is the row. They happen to match on this firing.

Loading by the walk’s firm instead of `pointer.id` loses because claim 10’s id predicate uses the pointer, and the firms Get already points at ids that are not a substitution of the walk.

A provision history, with “the firm now” as a latest read, loses because that split was the audit problem. The readers and the primitives ask for the current artifact. The audit append is already the history, on a table the write-set does not name. No migration.

Adding `firms`, `campaign_states`, `users`, `access_links`, or `audit_events` loses because the write-set names `ct_firms` alone. Mapping `firmId` inside `writesFromPayload` loses because claim 7 refused a second channel. Adding `contact_records` loses because this firing does not write that table, and the dispatcher’s fill is a separate argument. Adding `ct_firms` to `PERSON_WRITE_TABLES` loses because the row is the artifact and the id would become a person.

Selecting some newest firm, or filtering to `posture = 'Idle'`, loses because this firing has the id, and a conflict leaves posture alone. Retuning that conflict so a re-provision returns to `Idle` loses because the pointer names the row either way, and the existing `UPDATE` already chose not to assign posture. The campaign-state reset is a different table.

Dispatching pool allocate as this event loses because that handler does not call it. Falling through to `firms` when `ct_firms` misses loses because the seat’s union is a display read and the write-set named the CT table.

Dropping `firmId` loses because the matcher and the firm axis already read it, and unlike claim 13 the key is already on the payload. Dropping `firmName` or `email` loses because both are already present and `email` is not on the row. Adding posture, website, role, or the specimen’s consultant email as root scalars loses because posture is a column, and the others are not stored. Copying the row onto the pointer loses because `loadWriteField` re-reads. Requiring `RETURNING` loses because the id is the string the handler already bound.

No founder question. The write-set chose the table. The primary key chose `id`. The Get and door 1 already point at that id without a person. A listener that is already subscribed starts from this firm row. A later update of that id is visible on the re-read. The consent pair stays on the consent table.
