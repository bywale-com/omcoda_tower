## What the session was trying to establish

A later reader of the chronology has to be able to tell a refusal from a dry run and from a message that went out. Journal 014 had already shown three tick files and a fourth on the first step. The escalation writes a send engagement only when `send.ok`, so a halt deny leaves `window_fired` and no send row. The cell advance writes `send_dry_run` unless the send is a live success, stores the send object, and has already written `cell_advanced` with `delivered` true. The wait-until arm discards the `DispatchResult` and always writes `send_dry_run` with no send object. `enrollAndActuate` labels `send_live` or `send_dry_run` from `shouldLiveSend` and stores the send object, including a deny, and that write runs only after the enroll check has passed. Desk-14 says the chronology of what already fired stays complaint-ready. Those shapes are different files. The writers branch on `send.ok`, not on `detail`, so a silenced deny and a consent-missing deny have the same shape as a halt deny. The question was which record the product already requires, and whether the words the licensee reads — a test send, or a refusal — were still a founder choice.

## What the table and the dispatcher already are

`engagement_records` is an append log: `id`, `firm_id`, `contact_id`, `event_kind TEXT NOT NULL`, `payload`, `created_at` (`supabase/migrations/004_machine_tables.sql`). There is no check on the kind. `writeEngagement` inserts `eng-` plus a uuid and returns that id (`cascade.ts`). `SYSTEMS-STORY` §7 says the engagement record is a chronology of events that already fired and that it authors nothing. Leaf 1.1 names the consultant panel as those chronology rows, record only. `CLIENT-DATA-BIND` binds Activity to this table plus `active_attempts`. The tick does not dispatch an event for the send, so the row is not a listening pointer and it is not an element of `payload.writes`.

`DispatchResult` is already three shapes (`dispatchSend.ts`). A live accept is `ok: true`, `dryRun: false`, and a `messageId`. A dry run is `ok: true`, `dryRun: true`, and a `reason`. A deny is `ok: false`, a `deny` string, and an optional `detail`. `dispatchEmail` returns the gate deny before the cohort short-circuit. Its comment calls the cohort path fail-closed to dry-run, and says halt still denies. `ACTUATION-REPORT` defines that dry run as `SEND_MODE` and the cohort: anything else stages the send and does not blast the book. A missing address inside `actuateChannelSend` returns the dry-run claim 20 had already left outside the gate. The three tick calls pass purpose `cem` and only run when the channel is email or text.

The escalation is the only tick writer that already follows those three shapes. `send_live` is written only for a live accept, with `messageId`, `subject`, and `bodyText`. `send_dry_run` is written only for a dry run, with `reason` and the same copy. `ok: false` writes nothing beside the `window_fired` row that was inserted before the send. The cell advance computes `shouldLiveSend` and writes `send_live` only when that flag is true and the result is a live accept. Every other result, including a deny, is `send_dry_run`. The payload stores the whole `send` object. `reason` is set only when the result is a dry run, so a deny has neither `reason` nor `messageId`. The wait arm ignores the return and writes `send_dry_run` with `subject` and `bodyText` and no `send` object, for a deny, a dry run, and a live success alike.

## What the desk does with the kind

The consultant chronology is the file desk-14 is talking about. `titleFor` turns `send_live` into `Send · {channel} (live)` and `send_dry_run` into `Send · {channel} (dry-run)`. An unknown kind becomes the kind with underscores replaced by spaces. `outcomeFrom` says `Outcome · dry-run ({reason})` when `payload.reason` is set, and `Outcome · accepted` when `payload.messageId` is set. It does not read `payload.send`. The inspector replays whenever `subject`, `bodyText`, or `bodyHtml` is present. `HUB-STRUCTURE-SYSTEM-BIND` item 76 says a body shown in replay is what was sent or dry-run staged. `CLIENT-DATA-BIND` says the cascade writes that copy so dry-run and live both replay. The operator Agents table is a second reader: `eventKindProse` returns `Sent` for any kind that contains the substring `send`, and it checks that before it checks `halt`.

The Sent and Delivered tags are not the kind. `signalsFrom` and the inspector milestones light `Sent` when the projected kind is `send` or when `active_attempts.state.delivered` is set, and they light `Delivered` from that same flag. `CLIENT-DATA-BIND` says those tags come from attempt state. Claim 20 left `delivered` true on the cell, because `criteriaDue` treats it as the delivered condition. A deny row does not turn the tags off.

`attempt_nullified` is the stop the log already records as its own kind. The inbound override writes it and sets `status` to `nullified`. It sits beside the rows that were already there. It does not reuse `send_dry_run`, and it does not record the stop by omitting a row. `hasInboundOverride` reads only `inbound_reply`, `form_visit`, and `inbound_override`. A send kind is not that scan.

## How the reading changed

The first reading was that the escalation had already chosen, and the record of a deny is no send row. That lost once the other two tick paths were put beside it. A `window_fired` with no send row is also a channel that never called `actuateChannelSend`, and a window that was still waiting. The wait arm is the later send for that waiting window, and it writes no `window_fired` of its own at the moment it sends. Omitting the row there removes the moment from the log. Item 68 of the bind says a halt is visible as the worker skipping the send. A hole does not say skipped. Desk-14’s competency, cited on that seat, is an accurate record of what occurred. The refusal occurred.

The second reading was to standardize on the cell: always write `send_dry_run` for anything that is not a live accept, and store the `send` object so a careful reader of the raw payload can see `ok: false`. That lost for the label the licensee actually reads. The list title is the kind. `send_dry_run` is the dry-run title, and the dry run is a specific `ok: true` result the dispatcher already separates from the deny. The escalation already refuses that kind unless `send.ok && send.dryRun`. Storing the withheld subject and body on a dry-run row makes the inspector replay a message item 76 treats as sent or staged. The wait arm’s version of the same label stores neither the object nor a reason, so even the raw payload cannot tell the three results apart. `enrollAndActuate` is a worse copy of the same mistake when `shouldLiveSend` is true: the kind is `send_live` while `ok` is false. That write is not a tick send. It was left for the next move.

The third reading was a founder question about the words. A test-send label and a refusal label are different experiences, and the handoff had said that split can be one the founder still has to make. It is not, once the desk and the kinds are in the same frame. The dispatcher, the escalation’s two `send.ok` branches, the actuation report’s dry-run definition, and the two titles already say which file is a test and which file went out. The third result is the one those two kinds do not name. `event_kind` is unconstrained text, and the bind treats a new kind as a row rather than a new table. `attempt_nullified` is the precedent that a stop is appended under its own kind. The complaint desk’s default title is the kind with the underscores turned into spaces, so `send_denied` reads there as `send denied`. That is the refusal, without a new sentence on the screen.

The operator helper’s substring was the last reason to doubt the token. `send_denied` contains `send`, so `eventKindProse` returns `Sent`. Naming the kind `policy_deny`, or anything else that dodges the substring, would keep that helper honest without a change, and it would also be the wrong word for a throughput deny. The writers do not branch on `detail`. The two allowed outcomes are already `send_live` and `send_dry_run`. The third result of the same call belongs in that family. The helper is a different surface from the engagement record. It was not retuned.

The tags were the other experience that could have been reopened. They say Sent on a cell whose send was denied, because `delivered` is true. The bind already attaches those tags to attempt state, and claim 20 already kept the flag because the attempt clock reads it. The tags stay the flag. The kind is the refusal. Retuning the tags would make them a second story about the provider, which is the row’s job.

## What was settled

A tick send with `ok: false` appends one `engagement_records` row, kind `send_denied`, through `writeEngagement`. The payload carries `attemptId`, `channel`, and the `send` object as the dispatcher returned it, plus the step keys that writer already stores: `runId`, `criteriaId`, and `criteriaLabel` on the escalation; `cellId`, `cellLabel`, and `runId` on the cell; `attempt_n` on the wait. Subject, body, `messageId`, and `reason` stay off that payload so replay does not present a withheld message as a send or a stage. An allowed result uses the escalation’s two kinds, including on the wait arm, which has to keep the `DispatchResult` to do any of this. `send_live` keeps `messageId` and the copy. `send_dry_run` keeps `reason` and the copy. The cell’s `shouldLiveSend` conjunction is not the label. `window_fired` and `cell_advanced` stay. The attempt stays open. The deny does not enter the inbound scan and does not nullify. The same kind covers halt, silence, consent missing, and throughput, because the branch is `send.ok`. `detail` rides along on the object and is not interpreted. The consent select was not specified. No migration. No founder question.

The first step was not labeled. A halt already stored returns before that write. A deny that still reaches it is filed from `shouldLiveSend`, which can say `send_live` for a message that did not leave.
