# Journal 001

The session started in the Operator’s Configuration Libraries, on Agents and Automations, with a narrow question: can the product actually keep one execution’s result from being consumed as another’s? The face documents were the intended behaviour. The walker, the completion matcher, and the contact seat were the implementation. Nothing was changed in the product.

## What the two modules are for

`docs/README.md` still carries the 15:43 flag. Agents is where the operator defines a sequence, per firm or as a default plus overrides, with attempt rules, and a goal that is itself an escalation point: another agent, a workflow, or it ends. Once met, met.

`docs/register/AGENTS-FACE.md` makes the sequence a blank container of campaigns. Each campaign has one objective. Meeting it is what allows the next campaign. Enroll starts that mission now. It is not waiting on an event.

`docs/register/AUTOMATIONS-FACE.md` is the other module, entered from Agents rather than invented beside it. On an event, perform an operation, and branch on the kind of result. All objectives are events. The write-back is the event. Law 33: when a node finishes, the next step has every write that run made. `docs/register/PRIMITIVES.md` says the same thing and separates the two doors. On this canvas, the next node holds a handle to those writes. A different automation may hear the completion as an event. One is not a substitute for the other.

Packet 022 (`docs/register/SYSTEMS-CHANGE-PACKET-022.md`) is the machine reading of the flagship. Objective met is a Local event. The latch is `enrollment.campaign_id`. History is an `engagement_records` row of kind `objective_met`. No new goal table. Escalation is a workflow subscribed to that event, whose action enrolls an agent.

That is a closed enough picture to test. Many firms, many workflows, many enrollments, many nodes. If a later step cannot name which of those produced the row it is about to read, it will read someone else’s.

## The first reading was stale

`docs/register/SYSTEMS-AUTOMATIONS-NODE-OUTPUT.md` says the live walker does not pass module output to the next node, and that `WalkContext` is only a trigger payload plus contact ids. That packet is dated as the question SA had circled. It was the obvious place to start, and it would have sent the rest of the session at re-specifying a handle the code already has.

`server/wire-service/workflowWalk.ts` now keeps `previousWrites` and `chainWrites`. `commitWrites` stores the node’s pointers. `mappedWrites` resolves a chip’s `fromNodeId` against that map. `server/wire-service/runWrites.ts` defines the pointer as table, id, and optional contact. The header comment on the walker is still the old “v1 linear walk” sentence. The body is not. For one invocation that never parks, the next node can see what the earlier nodes wrote, and it sees pointers rather than a copied payload. That matches the primitive: the rows live in the module, the graph holds the handle, and the handle is not the whole database.

The node-output document stays the product statement. It is not the inventory of the walker. The session’s first conclusion — “there is no handle” — was revised here.

## Where the handle dies

The run’s identity is `workflow_run.id` (`supabase/migrations/004_machine_tables.sql`). On park and on finish, the walker writes `node_status` JSON, and each node’s status includes its `writes`. That is enough to rebuild `chainWrites` after a restart. Resume does not do it.

`resumeDueWaitingRuns` loads waiting runs whose `resume_at` has passed, marks `wait_occupancy` approved, and calls `resumeWaitRun` with those occupancy rows, or with `counts.waitWrites` if there are none. `resumeWaitRun` starts `walkValidatedWorkflow` with `triggerPayload.writes` set to that list and `resumeFromNodeId` set to the wait. The new context’s `chainWrites` is `{}`. The prior `node_status` is copied onto the status object so the eventual UPDATE still contains it, but nothing reads those writes back into the map. A chip that names a node from before the Wait falls through to the wait’s own pointers.

A duration wait never inserts occupancy. It only stashes `ctx.previousWrites` on `counts.waitWrites`, which is the last node, not the map. Same hole, slightly narrower.

So the in-memory handle and the Wait cannot both be true under the current resume contract. Packet 017 wanted every completed node’s writes available later. Migration `024_wait_occupancy.sql` made “later” a real resume. The resume forwards one node.

The decision is to rebuild `chainWrites` from `node_status` of that same `workflow_run.id`. A new run-write table was considered and rejected: the pointers are already stored, and a second table would be a copy of the handle the primitive says not to invent. Forwarding only the wait’s writes was the other option, and it is the bug.

## The listen door drops the firing

The same function that walks a canvas also starts a new run when an event fires. `dispatchEventToWorkflows` inserts a `workflow_run` and calls the walker with the event payload spread in, plus `anyPass: true`.

For `objective_met`, packet 022 and migration `021_objective_local_axis.sql` say the write-set is `engagement_records` and `enrollment`. `advanceEnrollmentCampaign` does three things in order. It flips `enrollment.campaign_id`. It inserts the engagement row, whose payload still names the campaign that was met, the completion, and the next campaign. It dispatches `objective_met` with the objective id, campaign id, sequence id, enrollment id, contact id, kind, completion table, and completion id. The engagement id, just generated, is not among them.

`writesFromPayload` will not turn that payload into pointers. It looks for a `writes` array, an import batch, or `contact_ids`. The dispatch uses `contact_id` singular. The separate `contactIds` argument fills `ctx.contactIds`, so the walk knows the person, and `previousWrites` stays empty. The If reads writes (`evalIfPick` → `loadWriteField`). It has nothing to point at.

Even if the engagement id were added, `loadWriteRow` would return null. It knows `enrollment`, `audit_runs`, `contact_records`, tags, import batches, verdicts, sequence-ready, and missing-fact signals. It does not know `engagement_records`, `fact_writebacks`, `meeting_booked`, or `wait_occupancy`. The write-set and the reader do not meet.

There is a second, quieter bypass. `anyPass: true` sets `eligibilityPass`. `evalBranch` returns true as soon as it sees that. Legacy branch nodes on an event run do not consult the firing at all. The If node is unaffected and simply has no writes. The decision is to stop forcing `anyPass` on event dispatch, and to put this firing’s engagement pointer and enrollment pointer on the new run. The enrollment row must not stand in for the engagement row, because the cursor has already moved.

Querying “the latest objective_met for this contact” was considered and rejected. Two pursuits, or two firings close together, would cross. Leaving the ids only on `triggerPayload` was rejected because the established pick is a write pointer, not a second channel beside it.

## Attribution uses the newest pursuit

That listen-door gap only matters if the event fired for the right pursuit. `onCompletionWrite` selects one enrollment: this firm, this contact, `campaign_id` not null, newest `enrolled_at`. Packet 022 §2.4 writes that query and comments that one sequence is open today.

`enrollAndActuate` does not keep that comment true. It always inserts. Halt can block a new enrollment. Nothing else does. `enrollment` has no unique pair on firm and contact. `advanceEnrollmentCampaign` moves one cursor and leaves every other enrollment alone. The flagship escalation is a listener that enrolls another agent. The first mission is still open if it still has a next campaign, and it is a different row even if the cursor went to NULL. “One open sequence today” is a description of the shortcut, not a rule the enroll path enforces.

So the matcher and the escalation cannot work together. With two open enrollments, a completion stamped for the older one is tested against the newer one’s objective, fails the stamp check, and returns. The pursuit that asked is never loaded. That is a false negative, not a double advance.

The false positive is `resolveFormStamp`. Given only firm and contact, it takes the same newest enrollment and, when the caller passed no objective, writes that objective onto the fact. When it also has no `form_ref`, it derives `form.${enrollmentId}.${campaignObjectiveId}` from that guess. Packet 022 says no stamp means no match, and that a send outside a sequence stamps nothing and is therefore never a completion. The contact seat’s fact handler calls `resolveFormStamp` with firm and contact only (`handleContactSeatFacts`). Every answer from that workspace becomes a completion of whichever pursuit was enrolled last, if that pursuit’s objective is a form.

The seat’s access link already has `enrollment_id` and `campaign_id` (`supabase/migrations/019_contact_seat.sql`). The fact handler does not pass them. `projectSeat` also re-reads the newest enrollment when it decides which objective the workspace is showing, so the link and the projection can disagree, and the fact stamp follows the projection’s shortcut rather than the link.

Click is the same shape. The webhook loads `firm_id` and `contact_id` from `outbound_messages` and ignores `enrollment_id` and `campaign_objective_id`, which migration 021 added. It then calls `onCompletionWrite`. The join inside `objectiveSatisfiedBy` could have started from the message. It only runs after the newest enrollment is chosen. A stamped click for the other pursuit does not match, and that pursuit is not advanced.

Meeting booking in `handleMeetingBook` stamps `meeting_booked` from the newest enrollment as well.

The decision is to attribute by the stamp that is already supposed to be on the row. For a form, parse `form_ref` when it has the derived shape, and do not recompute it from the newest enrollment. For a click, follow the send row’s `enrollment_id` and `campaign_objective_id`. For a meeting, use the ids on `meeting_booked` only when they were known at insert, not filled in by the newest-enrollment guess. Advance that enrollment only while its current campaign still asks for that objective. A bare fact, with neither `form_ref` nor an objective id supplied by the caller, matches nothing.

Refusing a second enrollment was the alternative. It would make the shortcut safe. It would also make the flagship escalation either a no-op or a silent replacement of the first mission. The face enrolls per sequence, and the enroll function already inserts. The product has chosen many pursuits. The matcher has to catch up.

## The cursor is also written by a history click

While reading the seat, `handleContactSeatGet` turned up as a second writer of `enrollment.campaign_id`. If the query string carries `campaignId`, it updates the newest enrollment’s cursor to that id. No objective check. `ContactWorkspace.tsx` “Open in Now” calls `loadContactWorkspace` with the history row’s campaign id, and `machineApi.ts` puts it on the query string.

Packet 022 is explicit that the flip is the latch and that it happens once, inside `advanceEnrollmentCampaign`, because the objective was satisfied. A history control whose label is “Open in Now” is asking to display an ask. Those cannot share `campaign_id`. The decision is that the seat load does not update the enrollment. The latch moves only when the stamped objective is satisfied.

This was not a founder question. Nothing in the face describes an override that retargets a running sequence from the contact’s history. The button is navigation. The server treated it as a write.

## Verdicts cannot remember which audit produced them

The handle is a pointer that is re-read (`loadWriteField`). That only works if the row is still the row this run wrote. `reachability_verdicts` and `sequence_ready` are primary-keyed by contact and firm (`004_machine_tables.sql`). `auditRun.ts` upserts them. The pointer’s id is the contact id. `loadWriteRow` does not even use the id; it selects by contact and firm and takes `rows[0]`.

A second audit of the same contact replaces the verdict. A node after a Wait, or any later reader, sees the other run. That is the primitive’s forbidden case (“not the latest audit for this firm”) embodied as a primary key.

Copying the values onto the pointer was rejected. The node-output packet and the primitives both say the module owns the records and Automations does not keep a shadow. The other housing is a row per audit run. The desk and the enroll gate (`machine.ts`, ready contacts for the firm; the contact list’s join) mean “current,” so they take the latest row per contact. One fact, two questions. This session did not alter those queries. The grain is the obligation.

`audit_runs` is already per run. The claim is only about the per-person results.

## What was not reopened

Packet 023 says a meeting nullifies open attempts because the person responded, and that this is a win, not a failure. `handleMeetingBook` and the contact seat both nullify every still-open attempt for the contact after `onCompletionWrite` has had a chance to mark the matched enrollment `met`. That contact-wide stop is already specified. Applying claim 3 to the meeting’s stamp must not be turned into “only this enrollment’s attempts stop.” The spending consequence and the attribution are different. Failure itself — exhaustion, one `campaign_failure`, still listening — was not walked. Lineage (who created the objective, the path, the time) was not walked. Form-as-node versus form-embedded-in-the-agent-action is still open on the Automations face and was left there.

## What the next investigator should do

The decisions above are made. The click path and the form path were both read far enough to see that they share the newest-enrollment pick. What was not done is to sit on `objectiveSatisfiedBy`’s click SQL with two concrete enrollments and confirm the false negative end to end, including whether `actuateChannelSend` actually persists the stamp that the webhook then ignores. That is a check of claim 3 against the send, not a new product question. The audit-grain readers listed in the specification should be confirmed as “current” before anyone changes the primary key; the list in claim 8 is the grep, not a finished audit of each query’s meaning.
