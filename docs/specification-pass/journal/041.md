## The window clock is a timestamp, and the budget is already a number

`window_started_at` is a `NOT NULL` timestamp on `active_attempts`. `hasInboundOverride` uses it as the lower bound of `engagement_records` for `inbound_reply`, `form_visit`, and `inbound_override`. `clockAnchor` prefers `form_started_at`, then `delivered_at`, then `opened_at`, and otherwise returns `window_started_at`. The comment says a re-entry does not reset the clock. `advanceTemplateCellIfDue` uses the column only when `state.enrolledAt` is missing. The wait-until arm in `tickOnce` writes the column to now after deleting `attempt_wait_until`, which is how the next local attempt opens its window. Nothing in `webhooks.ts` reads the column. A soft bounce cannot be a count stored in a timestamp, and moving the timestamp would start a new attempt window the bounce did not earn.

The number that already bounds attempts is `attempt_count`. `escalateAttemptWindow` reads it only after the channel ladder has nowhere to go. The read is the enrollment’s `campaign.attempt_count`, then the row `seq_attempt_cycle` with id `sac-global`, then `1`. Null falls through. A stored zero would be kept. Migration `010_sequence_campaign_housing.sql` seeds `sac-global` at `3`, with `wait_after_last_failed_seconds` `86400`. The Agents settings screen and the sequence settings screen label the figure “Number of attempts.” The campaign card labels it “Attempt count.” `docs/register/OPERATOR-REVISIONS.md` §5b says attempt N is a local retry under the channel that failed, and the Sarah chart is attempts 1, 2, and 3. The code starts `attempt_n` at `1` when the state omits it, and queues another cycle only while `attempt_n` is below the max. That queue also sets `attempt_wait_until` and returns the owner to the head of the channel order.

`handleAttemptCyclePut` stores a sequence override as `sac-seq-` plus the sequence id. The ladder never reads that id. It also never reads `campaign.override_this`. The column value is what the running cycle uses. Two budgets for one label would let the sequence screen stop soft mail while the cycle still retried, or the reverse. The soft bound uses the read the ladder already performs. When the attempt has no campaign, the soft check still continues at `sac-global`, then `1`, so a missing campaign is not an infinite retry.

## A deferral still has no window

The handoff’s next item was `email.delivery_delayed`. The page at `https://resend.com/docs/webhooks/emails/delivery-delayed`, fetched this session, says the event is a temporary issue, with a full inbox or a transient receiving server as the examples. The payload fields are `to`, `from`, `email_id`, `subject`, and the usual ids. `from` is the sender, including a display name. There is no receiving-server field and no retry-after. `deliv-23` asks for an adaptive per-provider throttle and a backoff inside the provider’s window, and it states no count and no duration. The paper path’s delay is “within provider backoff window,” on a `provider_throttle_state` this schema does not have.

One delay does not pause the firm. That would hold every contact because one mailbox was full, and claim 53 is already the unit path. The delay does not count as `bounce_soft`, which claim 55 already separated and claim 56 repeats. It does not write `attempt_wait_until`. That wait is the failed-last-node gap, defaulting to a day, and `tickOnce` advances a due cell before it consults the wait, so borrowing it would not even hold the calendar it seems to name. The email channel’s `within_seconds` of `86400` is the not-opened window. None of those figures is an ISP backoff.

What the payload cannot settle is whether the next email to that same address waits, and for how long. The page’s two examples are different grains, and the body does not say which one happened. Treating the recipient domain as the provider would pause every address at that domain because one inbox was full, and a custom domain is not the receiving server. That choice stays open. It is the founder question this session is leaving, because the product’s direction requires a provider window and the event does not carry one.
