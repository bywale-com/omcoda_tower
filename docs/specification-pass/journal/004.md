# Journal 004

The session began from `docs/specification-pass/NEXT.md`, then the standing specification, then journal 003. The named move was how `loadWriteRow` loads `engagement_records`, `fact_writebacks`, `meeting_booked`, and `wait_occupancy` by the pointer it is given. The start points were the null return at the bottom of that function, and the generic action in `workflowWalk.ts` that calls `writeEngagement` and then pushes `id: contactId`. The inserted id and the pointer id have to be the same id, or the re-read cannot see the row. The audit key stayed closed. The click, failure, and lineage stayed closed. The form path and the meeting path were not re-walked. No migration was written. No product code was changed.

## What the session was trying to establish

Claim 7 had already said a pointer the reader cannot load is not a handle, and that any table on a handle must be loaded by that pointer’s id. It had also said the listener must not treat the enrollment row as a substitute for the engagement row. Claim 8 had specified the audit load as the pointer’s identity, not “latest”, and those two tables have no column named `id`. Journal 003 left the four null tables as the open gap, and named the generic action as the writer that discards `eng-` plus a uuid. What it had not done was say which key each of those tables actually has, what the insert returns, what the pointer stores, or which of the ways of loading a row the product had already chosen.

## The null return, and the keys

`loadWriteRow` in `server/wire-service/workflowWalk.ts` handles `sequence_ready` and `reachability_verdicts` by contact and firm, then `contact_records`, `contact_tag`, `audit_runs`, `import_batch`, `enrollment`, and `missing_fact_signals` by `WHERE id = $1`. Anything else, including the four tables, hits `return null`. `loadWriteField` calls that function and then `nestedField`, which walks a dotted path. A later node does not receive a column list. It receives the row, or null, and then the field it named.

The migrations give all four tables `id TEXT PRIMARY KEY`. `engagement_records` and `fact_writebacks` are in `supabase/migrations/004_machine_tables.sql`. `meeting_booked` is in `007_meeting_booked.sql`. `wait_occupancy` is in `024_wait_occupancy.sql`, and it also has `UNIQUE (workflow_run_id, wait_node_id, contact_id)`. `021_objective_local_axis.sql` adds `form_ref` and `campaign_objective_id` on fact writebacks, and `campaign_objective_id` on meetings. None of those additions replaces `id`. `005_actuation.sql` indexes engagement on `(firm_id, contact_id, created_at DESC)`. That index is what `hasInboundOverride` scans. It is not a second primary key.

This is the opposite of the audit tables. Those have no `id` column, so claim 8 had to say the pointer’s `id` is the run and `contact_id` is the person. These four already have the column the other id-keyed loads use. The audit pair does not transfer. No new column is required, which is why this pass writes no migration.

## The generic action drops the id it just inserted

`writeEngagement` in `cascade.ts` allocates `eng-` plus a uuid, inserts `id`, `firm_id`, `contact_id`, `event_kind`, and `payload`, and returns that id. The action fallthrough in `workflowWalk.ts` calls it once per `ctx.contactIds` with `event_kind` set to the action type and a payload of `workflowId`, `runId`, `label`, and `formQuestionIds`. It ignores the return and pushes `{ table: "engagement_records", id: contactId, contact_id: contactId }`.

The types that reach that fallthrough are `manage_lists`, `assign_task`, and `notify_consultant`. `ACTION_TYPES` lists them, and `action_type_check` in `010_sequence_campaign_housing.sql` allows them. `call_agent`, `ascribe_tag`, and `run_audit` return from their own branches. An in-app affordance other than those last two returns earlier with an empty write list and does not insert. `normalizeActionType` maps an unknown type to `call_agent`, so it does not fall through either.

`actionAgentRef` returns null unless the type is `call_agent`. `origin/pr-96:docs/register/SYSTEMS-AUTOMATIONS-ASCRIBE.md` A7 still says those three Hub names are silent and that nothing is executed. That sentence matches `actionAgentRef`. It does not match the fallthrough, which inserts a row and pushes a pointer. The session did not mint a list, a task, or a notify table, and it did not delete the insert. A7’s silence was considered as a reason to drop the pointer. It was rejected because the row is already written and the pointer is already pushed, and a pointer that names the contact cannot re-read an `eng-` id.

That mismatch is enough on its own. Two nodes of the same action type for one contact insert two rows and push two pointers with the same id, the contact. A loader that selected by contact, even the latest row, could not tell those two writes apart, and a Wait that re-read later would see whichever append landed last. Claim 7 and claim 8 already refused “latest” for the handle. `writeEngagement` already returns the distinguishing id. The pointer’s `id` is that return. `contact_id` stays the person.

Other engagement inserts were looked at only far enough to see whether they push a pointer. `advanceEnrollmentCampaign` still generates the `eng-` id inside the `INSERT` and still dispatches `objective_met` without it. That remains claim 7’s missing field. It was not recut. `escalateAttemptWindow` and the cell advance keep `engagementId` on the `TickFire` result. That result is not a `RunWrite`. `handleMeetingBook` inserts a second engagement row for `event_kind = 'meeting_booked'` and discards the id. `event_write_set` for `meeting_booked` names the meeting table only, so that side row is not a handle. `handleEngagementRecordsList` reads the firm’s newest hundred rows for the desk. That is a list, not the re-read of one pointer.

## What the other three tables put on the pointer

`handleFactWriteback` and `handleContactSeatFacts` insert `fwb-` plus a uuid as `id`. The fact response includes `{ table: "fact_writebacks", id: writeId }`. The dispatch payload carries `writebackId`, `fieldKey`, `contactId`, `form_ref`, and `campaign_objective_id`. It does not carry `writes`. The seat handler dispatches once per answer, so each firing is one insert. There is no walker insert of this table.

`handleMeetingBook` and `handleContactSeatMeeting` insert `mtg-` plus a uuid as `id`. The dispatch payload carries `meetingId`, `contactId`, `slot`, and `campaign_objective_id`. It does not carry `writes`. Meeting attribution was not re-walked. The id on the row is what the pointer has to store. How the newest enrollment gets stamped onto that row was left as claim 3 and claim 9 left it.

The approval wait inserts `wo-` plus a uuid, with `ON CONFLICT (workflow_run_id, wait_node_id, contact_id) DO NOTHING RETURNING id`, and pushes a pointer only when a row comes back. That returned id is the primary key. A conflict pushes nothing, because the attempted id was not inserted and `RETURNING` does not yield the existing row. `resumeDueWaitingRuns` and `waitNote.ts` select the occupancy and push `id: row.id` with `contact_id`. The unique triple is how those writers find the row. It is not stored on the pointer. The row is updated in place (`status`, `approved_at`, and the title restamp). Re-read by id sees the current row, which is what claim 8 already required instead of a snapshot on the pointer.

`eventTest.ts` `writeId` prefers `body.id`. Door 1 selects fact rows, meeting rows, and `objective_met` engagement rows with `SELECT *`, and `toWrites` therefore sets the pointer id to the primary key. Those specimen pointers already match claim 10’s load. They are the test contract’s sample, not the live firing’s handle. Door 1’s fact query is the newest twenty for the firm, and the meeting query is the newest ten. That ordering was not retuned. It is not `loadWriteRow`.

`writesFromPayload` never turns `writebackId` or `meetingId` into a pointer. It reads `payload.writes`, then an import batch id, then `contact_ids` or `contactIds`. `dispatchEventToWorkflows` spreads the event payload onto the trigger and passes `contactIds` separately. For these three events `previousWrites` is empty. The same shape was visible on `campaign_failure`, which sends `campaignFailureId`. That event was not followed. It is not one of the four tables.

## What a later node needs, and what was rejected

`resolveOperandText` picks a write and calls `loadWriteField`. Once the row is loaded, `nestedField` can read `event_kind`, `field_key`, `value`, `slot`, `status`, `payload.label`, `payload.campaignId`, and any other column or dotted jsonb path on that row. `PRIMITIVES.md` forbids specifying a field catalog. The load is `SELECT *`. The chip names the field.

The alternatives that were actually considered, and why they lost:

Loading by contact and firm, the audit way, loses because these tables’ primary key is `id` alone and they append. Claim 8’s pair exists because those tables have no `id` column.

Keeping the generic pointer as the contact id, and selecting that contact’s latest engagement, loses because two writes in one walk share the contact and a later append changes what a Wait re-reads. The function already returns the row id.

Loading a fact by `(contact_id, field_key)` latest loses for the same reason. That query is already `resolveRuleOperand`, for the rule’s current answer. It was not changed. Loading the newest meeting for the contact is `objectiveSatisfiedBy`. That matcher was not re-walked. A handle that used it would see a later meeting.

Loading occupancy by the unique triple loses because the pointer does not carry `workflow_run_id` or `wait_node_id`. The writers that emit the pointer already copy `row.id`. A second pointer shape was rejected under claim 7.

Adding `firm_id` to the id predicate loses because the six existing id loads do not, and the id is already unique. Firm isolation stays on the insert and on which walk holds the pointer.

Falling back from a missing id to `contact_id` loses because that is the generic action’s bug moved into the loader.

Upserting on contact, or adding a column, loses because the id column is already the key and an upsert would collapse distinct events into one row. No migration.

Copying the row onto the pointer loses for the reason claim 8 already gave. `loadWriteField` re-reads.

`engagement_records`, `fact_writebacks`, and `meeting_booked` are not in `PERSON_WRITE_TABLES`. `wait_occupancy`, `enrollment`, and `contact_tag` are. `PRIMITIVES.md` says a person-row write splits people. These three rows carry `contact_id` the way an enrollment does, and their id is a surrogate the way an enrollment id and a tag id are. They join that split: the If tests each contact against the pointer whose `contact_id` is that contact, and the load reads that pointer’s id. The live set still omits them, so today one write decides the branch for every contact. The row id is not a person. When several pointers share a contact, `find` still takes the first. That choice among rows is the chip filter already parked. It was not retuned. `personIdsFromWrites` already prefers `contact_id` for every table, so the person is available once the pointer carries it. The generic action already sets `contact_id`. It sets `id` to the wrong string.

No founder question. Contacts, book readiness, and the enroll gate are untouched. The operator still reads a field of the write this node made. Latest-by-contact would show a different row once two writes exist, and the primitive already forbids that. A7 does not ask the founder to choose a list module. The id column, the returned `eng-` id, and the wait writers’ `row.id` pick the predicate.
