## What `writesFromPayload` actually does with a payload

`writesFromPayload` in `server/wire-service/runWrites.ts` reads `payload.writes` first. When that value is an array, it maps each element to `{ table, id, contact_id }` and returns. `contact_id` is taken from `contact_id` or `contactId` on the element. An element with no string table or no string id is dropped. The function does not then look at `import_batch_id`, `contact_ids`, or `contactIds`. It never reads `writebackId`, `meetingId`, `enrollment_id`, or a singular `contact_id` on the payload itself.

`dispatchEventToWorkflows` copies the event payload onto `triggerPayload` and adds `eventName` and `anyPass: true`. `walkValidatedWorkflow` sets `previousWrites` from `writesFromPayload(triggerPayload)`. The trigger node commits that list onto the run. The separate `contactIds` argument becomes `ctx.contactIds`. It is not passed through `writesFromPayload`. Claim 7’s refusal of `anyPass` was left as it stood. This session did not recut it.

That early return is why the three payloads are empty handles today, and why adding the array is sufficient. The fact and meeting payloads have no `writes` and no `contact_ids` array. Objective uses `contact_id` singular. The fallback therefore contributes nothing, and `previousWrites` is `[]`. A reader of `writebackId` inside `writesFromPayload` would be a second channel. The function’s own order already prefers the array.

## What the write-sets name, and what each dispatch builds

`event_write_set` version 1, in `supabase/migrations/017_event_test_contract.sql`, names `fact_writebacks` alone and `meeting_booked` alone. `supabase/migrations/021_objective_local_axis.sql` names `engagement_records` at ord 0 and `enrollment` at ord 1 for `objective_met`. Packet 022 §2.7 is that same pair. Packet 022 §2.5 is the objective scalar payload: `campaign_objective_id`, `campaign_id`, `sequence_id`, `enrollment_id`, `contact_id`, `kind`, `completion_table`, `completion_id`. It does not mention `writes` or the engagement id.

`handleFactWriteback` inserts `fwb-` plus a uuid as `writeId`, then calls `runContactEligibilityCascade`, then dispatches `fact_writebacks` with `writebackId`, `fieldKey`, `contactId`, `form_ref`, and `campaign_objective_id`. The HTTP body includes `cascade: [{ table: "fact_writebacks", id: writeId }, …]`. That object is the response. The dispatch does not receive it. `handleContactSeatFacts` does the same insert and the same event inside the answer loop, one dispatch per answer, and adds `firm_id` on the payload. It returns the seat projection, not the write id. The id is still in `writeId` at the dispatch.

`handleMeetingBook` inserts `mtg-` plus a uuid, then dispatches `meeting_booked` with `meetingId`, `contactId`, `slot`, and `campaign_objective_id`. The engagement row of kind `meeting_booked` is inserted after that dispatch, with the id written inside the SQL. `handleContactSeatMeeting` dispatches the same event with `firm_id` added, and it does not insert an engagement row. `event_write_set` does not name `engagement_records` for this event. Claim 10 had already left that side row off the handle.

`advanceEnrollmentCampaign` loads the enrollment, and on the path that flips `campaign_id` it inserts `engagement_records` with `eng-${randomUUID()}` inside the `INSERT`. The jsonb is `enrollmentId`, `sequenceId`, `campaignId` of the campaign that cleared, `campaignObjectiveId`, `kind`, `completionTable`, `completionId`, and `nextCampaignId`. The dispatch that follows has the snake-case scalars from packet 022 §2.5, including `campaign_id` of the campaign that cleared, and it does not have `nextCampaignId` or the engagement id. A return before the flip does not dispatch. The only callers are `onCompletionWrite` in the same file and the tick in `cascade.ts`. Neither builds a payload.

`localRefFromPayload` reads `form_ref` for `fact_writebacks`, and `campaign_objective_id` then `campaign_id` for `objective_met`. It has no case for `meeting_booked`. Those scalar keys are how a local trigger decides it is this form or this objective. They are not how `previousWrites` is built.

## What changed once the payloads were set next to the write-sets

The first reading, from journal 004, was that the ids exist and the array does not. That held. The next reading changed the shape of the fix. The fact and meeting handlers already hold the primary key in a variable at the moment they dispatch. The objective handler does not, because the uuid is inside the SQL. `writeEngagement` already binds `eng-` plus a uuid, inserts it, and returns it. Holding that string is the whole difference for the engagement pointer. The enrollment pointer is not an insert. It is `enrollment.id` from the row just flipped (`id TEXT PRIMARY KEY` in `supabase/migrations/004_machine_tables.sql`). `contact_id` is that row’s `contact_id`. A re-read sees `campaign_id` already moved, which is the sentence claim 7 already required. `nextCampaignId` is on the engagement jsonb and absent from the dispatch scalars, so a listener that only had the scalars would not see the campaign the cursor moved to. That is why the engagement pointer stays mandatory and the enrollment pointer is not a substitute.

`pickWrites` filters by table, so a node that names `engagement_records` or `enrollment` does not depend on order. The array still follows the registered ord, engagement then enrollment. `personIdsFromWrites` uses `contact_id` when it is present. When it is absent, and the table is in `PERSON_WRITE_TABLES`, it treats `id` as a person. `enrollment` is in that set. Omitting `contact_id` on the enrollment pointer would publish the enrollment id as a contact. Both pointers carry `contact_id`.

The same handlers write other rows. Those rows are not this firing’s array. `handleFactWriteback` may insert `missing_fact_signals` (`mfs-`). The seat handler only deletes the answered signal. The fact write-set does not name that table. `executeRuleWrites` already pushes a pointer when the walk itself inserts a signal. That is a node on the canvas. Both fact handlers call `runContactEligibilityCascade` first. It inserts `eval-`, `eres-`, `sig-`, and `mot-` ids and dispatches `eligibility.changed` with the fact scalars, `anyPass: true`, and `motion: "reactivation"`, and with no `writes`. The write-set for that event names the four tables. They stay on that event. When no workflow fires, the function enrolls `tpl.reactivation.v1`. That enroll was seen and left. The meeting side engagement stays off `meeting_booked`’s array. The completion row stays off `objective_met`’s array. `completionId` is a field of the engagement payload. The fact and meeting events already point at their own rows on their own dispatches.

## Alternatives, and why they lost

Teaching `writesFromPayload` to map `writebackId` and `meetingId` loses because claim 7 refused a second channel, the function already returns on `writes`, and `objective_met` has no engagement-id key. `enrollment_id` is a scalar that would still need a private mapping. One array carries both objective rows. The audit completion and the upload already use it.

Leaving the ids on the scalars for the If to read loses for the reason claim 7 already gave. The pick is `mappedWrites` and `loadWriteField`.

Selecting the newest row of the write-set table loses for the reason claim 7 and claim 10 already gave. Door 1’s limits are the specimen, and its objective enrollments are not the engagements’ rows.

Putting every answer in the seat loop on one dispatch loses because the loop already fires once per insert. This firing’s handle is that insert. A batch would attach another answer’s row to this run.

Adding `contact_records` because `contactIds` is passed loses because the write-sets do not name that table, and the argument is the person list. With `writes` present, the contact fallback does not run.

Adding missing signals, eligibility rows, the meeting side engagement, or the completion row loses because the registered sets do not name them. Eligibility is already its own dispatch. The meeting side row does not exist yet at `handleMeetingBook`’s dispatch, and the seat path does not write it.

Dropping the scalar keys once `writes` exists loses because `localRefFromPayload` would miss `form_ref` and `campaign_objective_id`. A local trigger for one form or one objective would stop matching. Packet 022 §2.5 put those keys on the payload for that axis. They stay. They are not the handle.

Pointing the enrollment pointer at a new id, or at `nextCampaignId`, loses because the row that moved is the enrollment already loaded, and `nextCampaignId` is a campaign id on the engagement payload. It is NULL when the sequence ended.

Requiring `writeEngagement`, or requiring `INSERT … RETURNING`, as a different result loses because both yield the id the row stores. The fact and meeting dispatches already hold the id in the variable the insert used. The objective insert holds that same kind of variable. The generic action’s call to `writeEngagement` stays claim 10.

Copying the row body onto the pointer loses because `writesFromPayload` keeps three fields and `loadWriteField` re-reads. Door 1’s spread is the test response. Claim 8 rejected the snapshot.

Putting `firm_id` on the pointer loses because `RunWrite` has no such field and claim 10 left firm off the id predicate. The seat payloads that already carry `firm_id` as a scalar were left as they are. The machine payloads that omit it were left as they are.

No founder question. The operator’s If still reads a field of a row this firing named. The write-set chose the tables. The primary key chose the id. The audit completion and the upload chose the channel. Keeping `form_ref` and `campaign_objective_id` is the local axis those triggers already use. A listener on one objective starts from this firing’s engagement row and this firing’s enrollment row.
