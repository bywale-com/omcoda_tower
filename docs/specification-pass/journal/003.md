# Journal 003

The session began from `docs/specification-pass/NEXT.md`, then the standing specification, then journal 002. The named move was the key of the per-person verdict and the sequence-ready row, so a later audit does not overwrite a contact’s verdict or ready flag. The readers were already split. `handleContactRecordsList`, `handleOnboardingFire`, and `executeGet` mean who is ready now. `handleAuditRunGet` means the run in the URL. `eventTest.ts` `door1` for `audit.completed` means the newest complete run’s rows. `loadWriteRow` must load the row that run wrote. “Who is ready now” had to stay a read of that same grain. The click stayed locked. Failure (packet 023) and lineage (Automations law 29) stayed closed. The form path and the meeting path were not re-walked. No product code was changed, and no migration was written.

## What the session was trying to establish

Journal 002 had shown that the four readers are not one question, and it had left the grain unchanged. Claim 8 already said the per-person result belongs to the `audit_runs` id that produced it, and that the desk and the enroll gate read the latest row per contact rather than a second stored fact. It had also rejected copying the verdict onto the pointer. What it had not done was name the columns that keep two runs apart, say what `RunWrite.id` is once more than one row exists, or say which row is “latest” when a later audit does not mention that contact. Two ways of storing history can both avoid an overwrite and still disagree about who gets enrolled, and about whether a past run’s page still shows the people that run wrote.

## What the tables and the writer actually do

`supabase/migrations/004_machine_tables.sql` gives both tables the primary key `(contact_id, firm_id)`. `reachability_verdicts` has `verdict`, `details`, and `updated_at`. `sequence_ready` has `ready` and `updated_at`. Neither has an `audit_run_id` column. Neither has a column named `id`. `audit_runs.id` is already one row per run (`arun-` plus a uuid in the writer).

`executeAuditRun` inserts the run, then for each contact upserts `contact_records` on `id`, upserts the verdict on `(contact_id, firm_id)` with `details` set to `{ auditRunId, rationale }`, and upserts `sequence_ready` with only the boolean. The pointers it pushes are `{ table, id: contact.id, contact_id: contact.id }` for both result tables, and a separate `{ table: "audit_runs", id: runId }`. The summary stored on the run is the counts `{ contacts, ready }`, not the per-person rows. The verdict is has-email and has-phone: both channels reachable, one channel partial, neither unreachable. `ready` is true unless the verdict is unreachable. The header says the walker calls this module and must not recode the verdict grain. The commit that added the file (`7980c43`) is the walker calling the real Audit module. That comment is not a specification of the primary key. The contact upsert is a different fact: one person, updated in place. The key under investigation is only the two result tables.

`loadWriteRow` then ignores the pointer id and selects `WHERE contact_id AND firm_id`, taking `rows[0]` with no order. With the current primary key that is the only row, and a second audit has replaced it. The same query would not name a particular run once several rows existed.

## The readers, sat on the queries

`handleContactRecordsList` left-joins both tables on `contact_id` and `firm_id`, in the session scope and in `every_firm`. One contact, one verdict, one flag, because the key allows one row. `handleOnboardingFire` selects `contact_id FROM sequence_ready WHERE firm_id=$1 AND ready=true` and enrolls those contacts. It does not look at `audit_runs`. A contact who was ready, and who is absent from a later audit, stays in that result, because the upsert never touches them. `executeGet` for `contacts` selects `contact_id` from both tables with no `firm_id` and pushes pointers whose id is the contact id. The missing firm predicate was seen again and left. It is not the key. Contact ids on `contact_records` are a single primary key, so the same id is not two firms’ people.

`handleAuditRunGet` loads `audit_runs` by the path id and the firm, then verdicts where `details->>'auditRunId'` equals that id, and left-joins `sequence_ready` on contact and firm only. Book readiness is that page. `BookReadinessModule` calls `getAuditRun` for the selected run and paints `detail.verdicts`. The create handler returns the in-memory `verdicts` array from `executeAuditRun`. The list’s later load is the re-read. Once the next audit replaces `details`, the older run’s page loses the contact, and the ready value on it was never that run’s flag.

`door1` for `audit.completed` takes the newest complete run (`status='complete'`, `started_at` descending, limit 1), then verdicts by `details->>'auditRunId'`, then `sequence_ready` for those contact ids with no run column. The file calls door 1 the live instance. It is the newest complete run’s specimen, not the enroll gate.

The inserts happen before `UPDATE audit_runs SET status='complete'`, and each statement is its own query. The desk and the enroll gate can see a row before the run is marked complete. Door 1’s complete-only filter is a different question. Applying it to the enroll gate would hide a run that had already written rows.

The two sentences are the desk’s current mark and the handle’s problem from claim 8. They are not a choice between them. The Contacts column shows the latest. The parked If and the run page need the row that was not replaced.

`eligibility_results` is already many rows per contact: its own `id`, an `evaluation_id`, and an index on `(firm_id, contact_id, created_at DESC)`. `handleBoardDetections` reads `DISTINCT ON (contact_id) … ORDER BY contact_id, created_at DESC`. That is “who is current” as a read of the same rows. It settled the prohibition on a second stored flag. It did not settle a surrogate id for the audit tables, because those rows are not what `loadWriteRow` loads, and the audit pointer is already `{ table, id, contact_id }`.

PR 110’s Systems Analyst log still records the live primary key as `(contact_id, firm_id)`. It does not ascribe a different one. The node-output inventory still names the two tables and the three verdict values. Nothing there required a new table or a run-level pass/fail.

## How the pointer can name one row

`RunWrite` has `table`, `id`, and `contact_id`. `evalIfPick` walks `ctx.contactIds` and finds the write with `contact_id === contactId || id === contactId`. `personIdsFromWrites` prefers `contact_id`, and only if that is missing does it treat `id` as the person for these tables (`PERSON_WRITE_TABLES`). The house If in `supabase/migrations/015_house_notes_handle.sql` is `pickTable: sequence_ready`, `pickField: ready`. It does not go through a chip id. So the person half of the key has to stay `contact_id`, and these pointers have to keep carrying it. The run id must not be used as a person.

`loadWriteRow` receives one write. A sibling `{ table: "audit_runs", id: runId }` sits on the audit node’s write list, but `executeGet`’s latest rows are not one run. A contact the later audit skipped still has the older run as their latest row. One sibling run id would be the wrong run for that contact. Claim 7 already rejected a second channel beside the pointer. The person pointer has to carry the run itself.

The two fields the pointer already has are enough. `id` is the `audit_run_id`. `contact_id` is the person. `loadWriteRow` loads `audit_run_id = pointer.id` and `contact_id = pointer.contact_id` for the walk’s firm. It does not take the latest row, and it does not ignore `id`.

A column named `id` was the other way to give `loadWriteRow` a `WHERE id = $1` like `contact_tag` and `missing_fact_signals`. It was rejected. These tables do not have that column. `eventTest.ts` `writeId` prefers `body.id` and otherwise uses `contact_id`. The input pane copies `sample.id` onto the field chip, and `mappedWrites` filters `w.id === id || w.contact_id === id`. A new `id` column would become the specimen’s identity and the chip’s filter. The row’s uniqueness is already the run plus the contact, which is the pair the pointer can hold. Encoding that pair into one string was rejected for the same reason: it is a private format no other handle uses.

`door1` has to emit the same pointer once it is reading the run’s own rows: `id` is that run id, `contact_id` is the person. Live `writeId` will not do that by itself, because there is no `id` column and the fallback is the contact. That is part of following the key, not a second key. A chip that then stores the specimen’s run id will not match a later walk, whose run id is new. The house If does not use that filter. The pane was not retuned. It is named under distinct work so it is not mistaken for a hole in the key.

## What “latest” has to mean

The enroll query and the upsert agree on something the newest-run-header reading would break. The upsert replaces only the contacts in the loop. The enroll query returns every ready contact in the firm. A second audit of a subset leaves everyone else at their previous flag, and the Contacts join shows that previous verdict. Defining “now” as the person rows of the firm’s newest `audit_runs` row would drop the omitted contacts. Packet 018 is per contact, not per batch header.

So latest is the row with the greatest `updated_at` for that `firm_id` and `contact_id`. The column is already what the upsert refreshes, and a new insert gets it from the default `now()`. If two rows share the timestamp, the one whose `audit_runs.started_at` is later wins. Door 1 and the run list already order runs by `started_at`. A contact with no row is not ready, and the verdict is null, which is what the left join shows today. The desk and the enroll gate do not require `status = 'complete'`.

`handleOnboardingFire` must apply that latest row’s `ready`, not any historical `ready = true`, and it must include the contact once. `handleContactRecordsList` must show one latest verdict and one latest ready flag, or the join repeats the contact. `executeGet` must emit only those latest pointers, with `id` set to that row’s `audit_run_id`. Emitting every historical row would make `evalIfPick`’s `find` depend on unordered `rows[0]`.

`handleAuditRunGet` and door 1 do not use latest. They use `audit_run_id` equal to the path id, or equal to the newest complete run. Ready joins on that same `audit_run_id` and `contact_id`. `details->>'auditRunId'` is not the predicate. The rationale stays in `details` because `noteFromVerdict` reads `details.rationale` through `loadWriteRow`. Once that load is the pointed row, the note is that run’s rationale.

The primary key is `(audit_run_id, contact_id)` on both tables. `firm_id` stays required and is set from the run. It filters the desk and the enroll gate. It does not separate two runs. `audit_runs.id` is already globally unique. A later run inserts. It does not update the earlier row. Same run, same contact, one row.

## What was rejected, and why the product already picked

Keeping `(contact_id, firm_id)` and hoping `details.auditRunId` names the run fails on the next upsert, and `sequence_ready` has no `details` at all. A current-flag table beside history is the second stored fact the handoff forbade, and packet 018’s “no new table”. Copying the verdict onto the pointer was already rejected; `loadWriteField` still re-reads. The newest `audit_runs` header as “who is ready now” changes who gets enrolled. A surrogate `id` adds an identifier the pointer does not need and a column `writeId` and the pane would treat as the write. A sibling `audit_runs` pointer cannot name `executeGet`’s mixed runs.

No founder question. Contacts still shows the latest mark. Book readiness still shows the opened run. The enroll gate still enrolls whoever is ready now, including someone the later batch did not mention. The surrogate would not change those three screens. The pointer’s two fields and the absence of an `id` column pick the pair.

The requirements file says `sequence_ready` is derived from the verdict and consent. The writer sets the boolean from the verdict alone. `enrollAndActuate` does not mention consent. That derivation was not walked, and it is not the key. The key stores the boolean the writer produced.
